Prometheus 指标实名、时钟口径，与一张症状→代码路径→动作决策表

源码版本：**vLLM 0.21.0**（2026-05）。本系列锁定该版本，指标名以 0.21 的 v1/metrics/loggers.py 为准。

前五篇讲了调度器内部。这一篇带着这些知识读监控面板——线上出问题时，看哪几个数、它们分别对应哪段代码、该采取什么动作。

## 1. 三组指标：容量、缓存、队列

所有指标都在 `vllm/v1/metrics/loggers.py` 注册，**名字以 `vllm:` 开头**（旧教程里的 `vllm:gpu_cache_usage_perc` 等名字在 v1 已不存在）：

| 指标 | 类型与单位 | 对应代码 | 看什么 |
| --- | --- | --- | --- |
| `vllm:kv_cache_usage_perc` | gauge，比例 | BlockPool 已用块/总块 | 容量水位，是否长期贴 1 |
| `vllm:prefix_cache_queries` | counter，**token** | 每请求被查询的 prompt token 数 | 命中率分母 |
| `vllm:prefix_cache_hits` | counter，**token** | 命中的满块 token 数（16 的整数倍） | 命中率分子 |
| `vllm:external_prefix_cache_queries/hits` | counter，token | KV connector 外部命中 | 与本地 APC 分开算 |
| `vllm:mm_cache_queries/hits` | counter，item | 多模态编码器缓存 | 第三组口径 |
| `vllm:num_preemptions` | counter，次数 | `_preempt_request` 每次 +1 | 是否在抢占风暴 |
| `vllm:num_requests_running` | gauge，请求数 | 在车上 | 与 max_num_seqs 对比 |
| `vllm:num_requests_waiting_by_reason` | gauge，按 reason 标签 | waiting，`reason=capacity/deferred` | 卡在容量还是异步依赖 |
| `vllm:corrupted_requests` | counter，请求数 | 输出 NaN（受 `VLLM_COMPUTE_NANS_IN_LOGITS` 开关控制） | 权重/KV 损坏信号 |

前缀命中率要自己除（token 口径）：

```
rate(vllm:prefix_cache_hits_total[5m])
/ rate(vllm:prefix_cache_queries_total[5m])
```

**没有预置的 P99**：延迟（`time_to_first_token_seconds`、`inter_token_latency_seconds`、`request_queue_time_seconds`、`e2e_request_latency_seconds` 等）都是 histogram，分位数要用 `histogram_quantile()` 对 bucket 现算。生产 SLO 盯 TTFT/ITL 的 P90/P99，不看均值。

## 2. 时钟口径：只减同源时间

`arrival_time` 在请求进入时打戳（跨 API/引擎进程，是前端墙钟），引擎内部迭代用自己的时间戳。做差值时只在**同一时钟域**内减——queue/inference 等分段延迟由引擎用同源时间算好，直接用；不要拿前端时间戳去减引擎内部的 iteration 时间。

## 3. 症状 → 代码路径 → 动作

| 症状（指标现象） | 对应调度器代码（前五篇） | 动作 |
| --- | --- | --- |
| 启动即 OOM、服务没起来 | 显存探测：请求额度 < 非 KV 开销（[篇 1](/blog/vllm-调度1-启动时块从哪来)） | 降 gpu_memory_utilization、减 TP 之外的常驻占用；区分”启动 OOM”不是运行时问题 |
| 运行中偶发 CUDA OOM | 实际激活/cudagraph 超 profile 估算 | 查 cudagraph 设置、降 max_num_batched_tokens |
| `num_preemptions` 持续上涨、P99 TTFT 尖刺 | 抢占循环 + recompute（[篇 4](/blog/vllm-调度4-块不够怎么办)） | 容量不足：减 max_num_seqs、上 KV 量化/更多显存、扩实例；这是 thrashing 信号 |
| waiting 高、running 长期到顶、请求不进场 | 准入闸门 full_isl 拦截（篇 4） | 同上扩容；检查是否被超长 prompt 队头阻塞（[篇 2](/blog/vllm-调度2-一个step里让谁推进)） |
| `waiting_by_reason=deferred` 高 | skipped 队列：等远程 KV/语法/流式输入 | 查 connector 与外部依赖，不是容量问题 |
| 命中率意外为 0 | get_computed_blocks 跳过查询（[篇 5](/blog/vllm-调度5-相同前缀为什么不用重算)） | 查 prompt_logprobs、pooling 模型、LoRA/salt/多模态 extra_keys、模板是否一致 |
| 命中率高但 TTFT 没改善 | 命中只省 prefill；远端命中要付网络代价（篇 8） | 联测 goodput 而非单看命中率；慢网时本地重算可能更快 |
| `corrupted_requests` 非零 | logits 出现 NaN | 查权重加载、量化、KV 损坏；不是调度问题 |

## 4. 块生命周期采样：默认关闭的深诊断

除了上述常驻指标，还有一个**默认关闭**的块级采样器 `KVCacheMetricsCollector`：开启后（config 里 `kv_cache_metrics=True`），对块分配做 1% 伯努利抽样，跟踪每块的存活时间、驱逐前空闲、复用间隔，输出 `kv_block_lifetime_seconds` 等三张 histogram。

它是诊断”缓存为什么留不住”的线索，不是精确账本——不开就零开销，按需临时打开。

## 5. 与后续专题的接口

当单机扩容到头、抢占仍频繁、命中率受多实例稀释时，问题进入集群层：前缀感知路由、全局 KV 池、PD 分离——这些系统手段见[篇 8](/blog/vllm-调度8-前缀缓存从单机到集群)。v0.21 的 PD 连接器仍标 experimental、只有传输层没有内置控制面，落地前以官方文档为准。

## 自测（答案点击展开）

**1.** 为什么不能直接拿一个”vLLM 命中率”数字和论文里的命中率比？要先确认哪三件事？

**2.** `num_preemptions` 持续上涨时，问题在调度器 bug 还是容量？先看哪两个指标区分？

**3.** 面板上有没有现成的 P99 TTFT？正确取法是什么？

**4.** `corrupted_requests` 非零应该去查调度策略吗？为什么？

<Expand title="▸参考答案">

1. 口径不同：vLLM 是 token 口径（命中 token/查询 token），且分本地 APC、外部 connector、多模态三组；论文常是请求口径或特定系统定义。先确认分子分母、是否本地口径、是否含外部命中。
2. 首先是容量 thrashing 而非 bug——抢占是分不到块时的正常路径。结合 kv_cache_usage_perc（是否长期贴 1）和 waiting/num_requests_waiting_by_reason 判断：水位满 + waiting 高 = 容量不足，扩容或降并发；deferred 高则是外部依赖。
3. 没有预置分位。延迟是 histogram，要用 histogram_quantile(0.99, rate(…_bucket[窗口])) 现算 P99。
4. 不该。它表示 logits 出现 NaN（开关 VLLM_COMPUTE_NANS_IN_LOGITS 控制），指向权重加载、量化或 KV 数据损坏，与调度决策无关。
