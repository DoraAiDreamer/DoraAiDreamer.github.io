四个计数器、schedule() 三阶段，以及为什么长 prompt 会队头阻塞

源码版本：**vLLM 0.21.0**（2026-05）。本系列锁定该版本，源码链接指向 v0.21.0 tag。

[篇 1](/blog/vllm-调度1-启动时块从哪来)解决了”有多少块”，这一篇回答引擎每一步在做什么。回顾 30 秒预告：引擎反复执行 **schedule（点名）→ execute（前向）→ update（记账）**。本篇拆开第一步——一次 `schedule()` 调用内部，到底按什么顺序决定”这一步算谁、算几个 token”。

## 1. 先认识四个计数器

要读懂调度，先分清请求对象（Request）上的四个数。用固定例子：**请求 R**（prompt 37 token、一个都还没算）和**请求 A**（22 token、已算 21、带 2 个投机草稿、1 个异步占位符）：

| 计数器 | 含义 | R | A |
| --- | --- | --- | --- |
| `num_tokens` | 已确认的 token 总数（prompt + 已生成） | 37 | 22 |
| `num_computed_tokens` | 其中**已经算过 KV** 的数量 | 0 | 21 |
| `num_tokens_with_spec` | 含投机草稿的目标长度 | 37 | 24 |
| `num_output_placeholders` | 异步调度预留的占位符（同步主线下为 0） | 0 | 1 |

> 占位符（placeholder）只在 async scheduling 下为正；同步主线是 0。它表示”上一步已经为这些位置预留了输出槽位”，首次遇到当 0 处理即可。

有了这四个数，一个 running 请求**这一步还需要算几个 token**，是一条减法（scheduler.py）：

```
num_new_tokens = (
    request.num_tokens_with_spec
    + request.num_output_placeholders
    - request.num_computed_tokens
)
```

代入例子：R 要算 37 + 0 − 0 = **37**（它的整个 prompt）；A 要算 24 + 1 − 21 = **4**。之后再受三道截断：长 Prefill 阈值、剩余 token 预算、`max_model_len`。

## 2. schedule() 三阶段

<Vllm2RecFig1 />

*图 1：running 先调度、无抢占才接纳 waiting、最后构造输出。Decode 不被饿死是结构顺序保证的。*

### 阶段一：running 请求，按队列顺序

```
while req_index < len(self.running) and token_budget > 0:
    request = self.running[req_index]
    num_new_tokens = request.num_tokens_with_spec + \
        request.num_output_placeholders - request.num_computed_tokens
    ...
    new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens, ...)
    # 块不够？抢占（篇 4），否则记账、扣预算
```

两个要点：

- **Decode 为什么不会被饿死**：每个 running 的 Decode 请求，追赶量天然就是 1（每步生成一个词）。调度器按队列顺序遍历，只要还有 token 预算就必得 1——这是结构性保证，**不存在”给 Decode 留百分之多少预算”这种比例机制**；
- `allocate_slots()` 在这里先当作黑盒：它要么返回分到的块、要么返回 None（失败就踢人）。黑盒内部是[篇 3](/blog/vllm-调度3-要N个token怎么摆进物理块)的内容，失败处理是篇 4。

### 阶段二：waiting 请求——有三个前置条件

```
# scheduler.py
if not preempted_reqs and self._pause_state == PauseState.UNPAUSED:
    while (self.waiting or self.skipped_waiting) and token_budget > 0:
        if len(self.running) == self.max_num_running_reqs:
            break
        ...
```

接纳新客必须同时满足：**这一步没有发生过抢占**、**token 预算还有剩**、**车上人数没到 `max_num_seqs`**。少一个都不接。

waiting 请求是第一次上车，要算的是整段（或一块）prompt，它的公式与 running 不同——直接用”总长度 − 已算”：

```
num_new_tokens = request.num_tokens - num_computed_tokens
```

### 阶段三：构造输出

把”谁、推进几个 token、分到哪些块、哪些是投机草稿、哪些带编码器输入”打包成 SchedulerOutput，交给 worker 执行一次前向；执行结果再经 `update_from_output()` 回写各计数器。

## 3. continue 还是 break：四种场景与队头阻塞

running 循环里有个容易看漏的设计——算不出 token 时用的是 `continue` 而不是 `break`：

```
if num_new_tokens == 0:
    # 流水线并行里 prompt 已调度但还没算完、编码器预算用尽等
    req_index += 1
    continue   # 跳过它，继续看后面的请求（不完全按 FCFS）
```

而 waiting 请求分不到块时是 **`break`**（scheduler.py：`if new_blocks is None: break`）——它假设队头是最短/最该先上的，**队头装不下，后面的一律不试**。

这带来一个真实的生产现象：**队头阻塞（head-of-line blocking）**。一个特别长的 prompt 如果当前预算和块都装不下，会一直卡在 waiting 队头，挡住它后面所有更小的请求，即使小车早就塞得下。这不是 bug，是 FCFS 下的有意取舍。

## 4. 控制切多少的三件配置（0.21 实测默认）

常被误传成”Decode 预留比例”，真实的三件套是：

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `long_prefill_token_threshold` | **0 = 不限** | 单个请求单步 Prefill 的截断长度；0 表示不截 |
| `max_num_partial_prefills` | **1** | 允许同时存在几个未完成 Prefill |
| `max_num_scheduled_tokens` | None | 调度器 token 预算硬上限；None 时回退 `max_num_batched_tokens` |

一个条件分支要注意（scheduler.py:244）：**当你把 `max_num_partial_prefills` 调到 >1 且阈值仍是 0 时，引擎会把阈值自动改写成 `max_model_len × 0.04`**；默认配置（partial=1）下不发生。

而 `max_num_batched_tokens` 这个真正决定每步总预算的值，会随硬件和使用场景分档：

| 硬件档 | API 服务（tokens / seqs） | 离线批量（tokens / seqs） |
| --- | --- | --- |
| ≥70GB 且设备名非 A100（H100/H200/MI300x） | 8192 / 1024 | 16384 / 1024 |
| 其他（含 A100，PR #17885 特判压回） | 2048 / 256 | 8192 / 256 |
| 类属性默认（仅供测试） | 2048 / 128 | 同左 |

加 `--performance-mode throughput` 且未手动指定时，预算和座位数翻倍。**所以在 H100 上”默认预算是 2048”是错的**——那是 A100 档。

## 5. 三个集合与两种策略

调度器手上并不是只有两个队列，完整的等待侧有三份：

- **waiting**：正常等待；
- **skipped_waiting**：被异步依赖卡住的请求——等远程 KV、等结构化输出语法编译、等流式输入；
- **step_skipped_waiting**：本步新跳过的请求，调度结束后插到 skipped **前面**，让新跳过的比旧跳过的先重试。

策略两种：**FCFS**（先到先服务，默认）与 **priority**（值越小越优先、平局看到达时间）。running 是一个列表而非队列，正是为了支持两种抢占选法——这是[篇 4](/blog/vllm-调度4-块不够怎么办)的内容。

## 6. 小结

一个 step 里，调度器先用**追赶公式**给在车上的请求各算需求、running 优先且 Decode 必得 1 个；再在”无抢占、有预算、没满员”三个条件下从队头接纳 waiting，装不下就 break 造成队头阻塞；最后打包成 SchedulerOutput。块到底怎么发、发不出来怎么办，分别是下一篇和篇 4。

**2.** waiting 请求在什么条件下才会被接纳？为什么 Decode 不需要”预留比例”也不会饿死？

**3.** running 循环里 `num_new_tokens == 0` 为什么用 continue，而 waiting 分配失败为什么用 break？后者造成什么现象？

**4.（配置题）** H100 上跑 API 服务，0.21 的默认 token 预算和座位数是多少？把 `max_num_partial_prefills` 从 1 改成 4、阈值不动，会发生什么？

<Expand title="▸参考答案">

1. num_tokens_with_spec + placeholders − computed = 37 + 0 − 0 = 37（整个 prompt 一个 step 吃进去，受 token 预算截断）。
2. 三条件：本步无抢占、token 预算 >0、running 人数未达 max_num_seqs。Decode 不饿死靠结构顺序——running 先调度，每个 Decode 请求追赶量天然为 1，遍历到就必得 1，与比例预算无关。
3. running 里 0 token 是暂时状态（流水线并行未完成、编码器预算尽），continue 跳过它还能服务后面的请求，是对严格 FCFS 的有意放松；waiting 的 break 假设队头最该先上、装不下后面也不必试，造成长 prompt 卡住后续小请求的队头阻塞。
4. H100 API 档是 8192 tokens / 1024 seqs。partial 调到 4（>1）且阈值仍为 0 时，引擎自动把 long_prefill_token_threshold 改成 max_model_len×0.04（scheduler.py:244）。
