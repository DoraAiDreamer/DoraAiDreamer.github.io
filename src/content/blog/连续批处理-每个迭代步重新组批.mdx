在[《一次推理的旅程》](/blog/一次推理的旅程-prefill与decode/)里我们算过一笔账：70B 模型 FP16 权重约 140GB，一张 H100 的显存带宽约 3.35TB/s，Decode 阶段每生成一个词，光把权重从显存搬到芯片上就要约 **42ms**，而这一步真正的计算只占零头。

看着这 42ms 自然会冒出一个问题：**搬一趟权重只换来 1 个词，那能不能让这一趟同时换来 30 个词？** 答案叫**连续批处理（Continuous Batching）**，它是今天所有高吞吐推理引擎的默认工作方式，也是 vLLM 调度器的灵魂。

先界定它解决问题的范围，避免一个常见误解：连续批处理不是「只管 Decode」的机制——它的定义（每个迭代步重新决定批次成员）对 Prefill 和 Decode 同样适用。但两阶段从它身上获益的方式不同：**Decode 的核心病症是槽位空转**（请求一个词一个词地生成、长度参差不齐，静态批处理下大量槽位在空等），这正是连续批处理直接解决、也是本文前 3 节的主线；**Prefill 的核心病症是独占迭代步**（一个长 prompt 算几百毫秒，同批 Decode 全部停摆），连续批处理只给了「可以把它插进批次」的前提，真正的解法是第 4–5 节的 **Chunked Prefill**（把 Prefill 切块后再按步混批）。一句话：机制通用，收益对症——Decode 靠它填空槽，Prefill 靠它+分块拆独占。

## 1. 先看旧规矩：静态批处理

**定义：静态批处理（static batching）** 指一次推理调用的请求集合在整个批次生命周期内固定不变——框架把 $b$ 个请求拼成一个固定形状（shape）的张量，中途既不允许请求提前退出，也不允许新请求加入，必须等批次中**最长的请求**全部生成完，这一批才释放。它是传统深度学习框架（固定形状张量）的默认执行方式。

打个比方：这像一场统一收卷的随堂测验——全班同时开考，但必须等最后一个人交卷，老师才收走所有卷子并开始下一场；早做完的不能离场、教室不能周转。计算槽位相当于座位、教室周转时间相当于新请求的等待。只看上一段的定义即可读懂，比喻可跳过。

用一个最小例子算清这笔浪费。设一次调用的批次大小为 4，4 个请求的输出长度分别是 50、80、100、200 个 token。记账单位定义为**槽位·迭代步（slot-step）**：一个槽位是批次中一个请求的位置，每个迭代步 GPU 为全部 4 个槽位付出一次完整前向，权重搬运量与该槽位上的请求是否已经完成无关。

| 迭代步区间 | 在跑请求数 | 空转槽位·步 |
| --- | --- | --- |
| 1–50 | 4 | 0 |
| 51–80 | 3 | 30 |
| 81–100 | 2 | 40 |
| 101–200 | 1 | 300 |

批次被最长的请求锁满 200 个迭代步，总开销是 200 × 4 = **800 槽位·步**；其中有效产出只有 50+80+100+200 = **430**，其余 **370 槽位·步（46%）是空转**——请求完成后它的槽位仍被占着，GPU 照样搬权重、做调度，只是没有有效 token 产出。而且 370 里有 300 集中在最后 100 步。

<CbStaticPainFigure />

*图 1：静态批处理的浪费——蓝色是有效前向，斜纹是请求完成后仍占用槽位的空转；批次外的新请求在整批结束前无法加入。*

第二笔浪费是延迟代价：**这 200 个迭代步内到达的新请求无法加入，必须等待整个批次结束**——引擎正在忙一个形状固定的张量，没有入口让它们在批次结束前加入。

这笔账有几个简化假设要交代：四个请求同时到达、每个迭代步墙钟等长、每请求每步恰好占一个槽位、中途没有新请求、也没算旧框架对输入做左 padding 的额外浪费。还要提前防一个过度解读：**真实流量到达稀疏时，任何调度机制都会有空槽**——46% 是这个简化模型下的上界，真实收益由请求的到达分布和输出长度分布决定。

## 2. 新规矩：连续批处理（迭代级调度）

**定义：连续批处理（continuous batching，论文称迭代级调度 iteration-level scheduling）** 指调度器在**每个迭代步**结束后重新决定批次成员：本步完成的请求立即退出并释放 KV Cache，等待中的请求只要显存允许就在下一步立即加入——批次的形状按步动态变化，而不是一次固定到批次结束。芯片每执行一次模型前向就是一个迭代步，所有在批请求在这一步恰好各前进一个 token。

<CbRosterFigure />

*图 2：第 $t$ 个迭代步在批请求为 A、B；一个迭代步后 B 完成退出、等待中的 C 被准入，第 $t+1$ 步在批请求变为 A、C。*

注意图 2 教的是强版本：**退出与准入在同一个迭代步边界同时完成**，不是先移除完成者、再等下一批。请求的生命周期因此是：到达后进入 waiting 集合 → 被准入进入 running → 每个迭代步前进一个 token → 完成后进入 finished 并释放资源。调度器维护三个集合：等待中的 waiting、在跑的 running、本步刚完成的 finished；每个迭代步固定三段——schedule() 做准入/退出/抢占决策、执行一次前向、update_from_output() 更新状态与计量。

这套机制出自 **Orca**（Yu et al.，OSDI 2022），论文里的正式名字是 **iteration-level scheduling**（迭代级调度）；「continuous batching 连续批处理」是 2023 年业界叫开的名字——Anyscale 当年在 continuous / dynamic / iteration-level 三个近义词里选定了 continuous batching。顺带注意别和微软的 Orca *模型*论文搞混，两篇同名但毫无关系。

### 多请求拼批为什么安全：两道隔离关卡

不同请求拼在一个迭代步里，最自然的担心是「它们会不会互相看到对方的内容」。安全靠两道分工不同的关卡：

1. **请求边界防止跨请求可见。** 不同请求之间必须有明确边界：Orca 的做法是在注意力之前 Split（拆开），每个请求单独算注意力；现代融合内核则把 cu_seqlens——记录各请求 token 区间起止位置的索引数组，即块对角式的边界索引——传给内核；如果用显式的 batch 维度，每一行天然隔离。
2. **因果掩码防看未来。** 它只在**每个请求自己的序列内部**生效：保证位置 $i$ 只看得到 $\le i$ 的内容，让「拼起来并行算」和「一个请求一个请求串行算」结果完全等价。因果掩码单独**管不了「不看别的请求」**——展平序列里 token 位置全局编号，位置更早的其他请求 token 在因果规则下是可见的，隔开请求的是第 1 道关卡。

这个口径和[《一次推理的旅程》第 2.1 节](/blog/一次推理的旅程-prefill与decode/)完全一致：掩码是「并行结果与串行等价」的保证，不是跨请求隔离的手段。

### Selective Batching：「能拼才拼」的原始定义

Orca 还配套了一项执行层技术，叫 **selective batching（选择性批处理）**。2022 年的原始定义要按历史讲：投影、FFN、LayerNorm 这些**带模型权重**的算子，把多个请求的 token 展平成张量拼批计算；**注意力当时反而要拆开、每个请求单独执行**——论文给出的理由是注意力不挂参数，拼批得不到「摊薄权重搬运」的收益，而各请求长度不一，拼起来还麻烦。

今天变长注意力内核（FlashAttention varlen、PagedAttention kernel）已经成熟，注意力也能按请求边界安全拼批，这条历史边界在现代引擎里基本消失了。所以别把它当成当前 vLLM 的行为描述——它是 2022 年的工程约束。

这套机制有六条必须钉死的边界（后文逐条展开）：

- **在批请求数有硬上限**：等于 KV 显存可容纳的槽位数，不能超载；
- 每个迭代步，在批请求**恰好各前进一个 token**（lockstep），不是连续生成；
- 准入只发生在迭代步边界，错过一步就等下一步；
- 迭代步墙钟时长随在批请求数与负载变化——这就是 TBT，不是常数；
- 新请求先过准入检查（第 6 节）才能进入 running；
- 已在跑的请求也可能因显存不足被抢占回 waiting（第 6 节），这不是常规路径。

<Expand title="展开：V1 引擎里队列与策略的实现细节">

- 调度器内部实际有 **waiting、skipped_waiting、step_skipped_waiting** 三个等待队列加一个 running 列表：被异步依赖卡住的请求（等远程 KV、等结构化输出语法编译、等流式输入）先放进 skipped；每步新跳过的请求收集在 step_skipped 里，调度结束后插到 skipped **前面**，保证新跳过的比旧跳过的先重试。
- 调度策略两种：**FCFS**（先到先服务，默认）和 **priority**（按优先级，值越小越优先，平局看到达时间）。
- running 是一个**列表**而不是队列：FCFS 抢占时直接弹出最后一个；priority 抢占时挑优先级最低的。
- 一条关键纪律：**某个迭代步一旦发生抢占，这一步就不接纳新请求**——先让被抢占的请求重新 Prefill，防止它饥饿。

</Expand>

机制清楚了，但「为什么值得这么折腾」的经济账还没算。下一节用开头的 42ms 算给你看。

## 3. 经济账：权重搬一趟，全批共享

Decode 是显存带宽受限的：一个迭代步里，**模型权重只需要搬一遍，同批 $B$ 个请求共享这一趟**。用开头的数字算（70B 抽象设备 / TP 聚合口径，每请求按 2K 上下文、KV 约 0.64GB，忽略计算与开销）：

| 在批请求数 $B$ | 搬运总量 $W + B\times\text{KV}$ | 单步耗时（÷3.35TB/s） | 每请求每 token |
| --- | --- | --- | --- |
| 1 | 140.6 GB | 42.0 ms | 42 ms |
| 8 | 145.1 GB | 43.3 ms | 5.4 ms |
| 32 | 160.5 GB | 47.9 ms | 1.5 ms |

你可以手算中间那行验证：(140 + 8×0.64) ÷ 3.35 ≈ 43.3ms，每请求成本 43.3 ÷ 8 ≈ 5.4ms。**单步只慢了一点点，每请求每 token 的成本掉了一个数量级。**

<CbCostFigure />

*图 3：堆叠柱——权重段每步固定 140GB，KV 段随人数增长；绿色虚线是每请求每 token 成本（示意，非实测）。*

用符号收口，先命名：$W$ 为权重字节、$B$ 为在批请求数、单请求 KV 为该请求的全量历史 KV：

$$
\text{单步耗时}\approx \frac{W + B\times\text{单请求 KV}}{\text{显存带宽}}，\qquad \text{每请求每 token}\approx \frac{W}{B}+\text{单请求 KV}
$$

这里 KV 的口径必须钉死：它是该请求**当前全部历史的 KV**（约等于上下文长度 × 每 token KV），Decode 每一步都要从显存重新读一遍、随上下文长度线性增长——不是「一个新 token 的 KV」。这也解释了表里看似矛盾的两列：**每请求成本随 $B$ 下降**（$W/B$ 项变小），**单步总时长随 $B$ 缓慢增加**（$B\times\text{KV}$ 项变大），说的是同一件事的两面。

$B$ 能不能无限大？三个硬约束：

1. **KV 容量**：每个请求的 KV 都要占物理块，块总数是硬上限（见[《PagedAttention》](/blog/pagedattention-给kv-cache装上虚拟内存/)）；
2. **max_num_seqs**：引擎对在批请求数有配置上限，限制内核形状与调度开销；
3. **TBT 预算**：$B$ 增大时单步总时长缓慢变长，通常在撞到前两个约束之前，延迟约束先到。

经济账到此成立。但如果进入批次的不只是 Decode 请求，还有一个几千 token 的长 prompt 呢？

## 4. 病理：长 prompt 独占多个迭代步

回忆 Prefill 和 Decode 的差别：Prefill 一次处理成百上千个 token，是**算力受限**的，一个迭代步装不下；Decode 每步只算一个 token，是**带宽受限**的。

这里要回应开头埋的问题：连续批处理允许请求按步进出，但**如果不分块，一个长 Prefill 仍然要连续占用多个迭代步**才能算完——它在每个步里都占着「未完成 Prefill」的槽位，新的准入逻辑也帮不上忙。问题的因果要钉准：**不是「长 prompt 算得慢」，而是「它独占了这些迭代步，而迭代步是全批共享的」**——这几步里，在批的所有 Decode 请求都无法推进，TBT 出现数百 ms 量级的尖刺，等待队列里其他请求的 TTFT 也一起堆高。所以 Prefill 侧需要的是连续批处理之外的第二块补丁：把长 Prefill 切开（第 5 节）。

<CbStallFigure />

*图 4：长 prompt 的 Prefill 连续占用第 1–3 个迭代步，三批 Decode 请求零推进，第 4 步才恢复生成。*

这个「共用节拍器」的比喻，在[《PD 分离》第 1 节](/blog/pd分离-把prefill和decode拆开部署/)里用心跳和深呼吸讲过：Decode 是约 20ms 一次的心跳，Prefill 是数百 ms 的深呼吸——这里的「数百 ms」是量级示意，随模型与硬件变化，对应的是关闭分块的旧引擎。

论文证据只留最小的一组。**Sarathi**（2023 预印本）最早系统地研究了这个问题：在 LLaMA-13B/A6000 上，让 Decode 与 Prefill 块同批执行的**边际成本**比 Decode-only 迭代低 **2.8–10 倍**——10 倍是小 batch、短序列下的上界（微观上是 1.2ms vs 12.49ms/token），而**端到端吞吐最高只提升 1.33 倍**。两个提醒缺一不可：这是 Decode 的**边际**吞吐、不是系统总吞吐；当前 V1 引擎已经内置了这套机制，这些数字代表 2023 年的历史空间，不代表今天升级 vLLM 还能拿到。后续的 **Sarathi-Serve**（OSDI 2024）把它做成「无停顿调度」：在尾延迟目标约束下，Mistral-7B/单 A100 的服务容量提升 2.6 倍（基线为 vLLM；服务容量即达 SLO 的有效吞吐 goodput，不是裸吞吐）。

怎么让长 Prefill 不阻塞 Decode 心跳？下一节就是答案。

## 5. Chunked Prefill：长 prompt 分块插入迭代步

打个比方：一个 2000 token 的长 prompt 若一次性处理，要独占 3 个迭代步，其他请求全部等待；分块后每步最多插入 512 token、4 步完成，其他请求每步照常前进。代价是这个请求的首字时刻（TTFT）延后，但每个迭代步的时长（TBT）从此有上界。只看后一段的机制描述即可读懂，比喻可跳过。

机制上，长 prompt 被切成定长的 chunk，每个迭代步的批次 = 全部 Decode 请求 + 当步恰好完整完成的短 prompt + **至多 1 个**未完成的 Prefill 块。两个旋钮别搞混：每步处理多少 token 由 token 预算（max_num_batched_tokens）控制；默认配置下「每步至多一个未完成块」其实是 **FCFS 加预算分配自然保证的**——0.21 的核心调度器并不直接读取 `max_num_partial_prefills`（该字段仅在 ROCm AITER 后端被用于 CUDA graph 定尺寸；细节与全部旋钮的消费方核查见 [《Chunked Prefill》第 8 节](/blog/chunkedprefill-把长prompt切成节拍器能消化的小块/)）。还有一条优先级纪律：**Decode 优先**——每步先调度 running 的请求，Prefill 块只使用剩余预算，保证 Decode 不被持续挤占。

<CbChunkFigure />

*图 5：长 prompt 切成 4 块、每步一块与 Decode 同批；绿色虚线处才产出首字 TTFT。*

这个机制不是免费午餐，三条代价必须写明：

1. **长 prompt 的 TTFT 被拉长**：它的 Prefill 要分多个迭代步、每步只能拿到剩余预算；
2. **裸吞吐可能略降**：分块拼内核的总效率略低于大块一次算完——换来的是 TBT 稳定和尾延迟约束下的服务容量提升，不是"开了就更快"；
3. **预算是延迟/吞吐旋钮**：预算调大，长 prompt 完成得快但 Decode 被挤占得多；调小则反过来。

<Expand title="展开：V1 的 token 预算默认值（0.21 / 0.29 快照）">

vLLM 0.21（2026-05）在无人为覆盖时，按硬件分档（判定条件原文：**显存 ≥70GiB 且设备名不含 "a100"** 才走大档）：

| 硬件档 | API 服务（tokens / seqs） | 离线批量（tokens / seqs） |
| --- | --- | --- |
| A100 及其他小显存档（＜70GB） | 2048 / 256 | 8192 / 256 |
| H100/H200/MI300x（≥70GB，A100 除外） | 8192 / 1024 | 16384 / 1024 |

0.29（发稿时最新版，2026-09-09）新增一档：显存 **≥160GB**（B200/B300 类）时，**API 服务也是 16384 / 1024**。

- Chunked Prefill 与上面的分档预算在 V1 中**默认开启**。
- A100 上盲目调大预算反而降吞吐：PR #17885 的实测是 Llama-3.1-70B **TP=2 时小预算 +36%、TP=4 时约 −2%（基本中性）**，测试条件为请求灌满的吞吐测试。结论不是"A100 必须调小"，而是方向随硬件代际 × 并行度 × 在线/离线而变，上线要按自己的负载复测。
- 启动时加 `--performance-mode throughput`，默认预算和在批序列数上限会**翻倍**（仅对未显式覆盖的值生效）。
- 以上均为版本快照（2026-09，以官方文档为准）。

</Expand>

每个迭代步还有一个更硬的约束：槽位（KV 显存）是有限的。显存不够时怎么办？

## 6. 槽位不足：准入检查与抢占

**第一道防线是准入检查**：引擎在新请求进入 running 前，按它的**完整输入长度**（ISL，Input Sequence Length，即 prompt）估算需要多少 KV 块、能不能装下——不是只算第一块——装不下就留在 waiting。对应配置 `scheduler_reserve_full_isl`，V1 默认开启，为的是防止分块 Prefill 先准入后失败、造成 KV 显存抖动。注意这是**可行性估算、不是物理预留**：通过检查的请求之后仍可能被抢占。

**第二道防线是抢占**：某个 running 请求在下一个迭代步的 KV 块分配失败时（注意：不是新请求抢走了它的块），触发抢占：

- FCFS（先到先服务）策略下，抢占**最晚进入 running 的请求**（LIFO，后进先出），保护更早到达的请求——最新准入的请求因此是头号抢占对象；
- priority 策略下，抢占优先级最低的请求；
- 被抢占的请求**释放全部 KV、进度归零**，回到 waiting 队首优先重新 Prefill。

<CbPreemptFigure />

*图 6：请求视角的抢占过程——running → 被抢占 → waiting 队首 → 重新 Prefill → 重新 running。*

按时间戳区分三代机制，别混用：vLLM 论文（2023）里有 **swap（把 KV 换出到 CPU 内存）和 recompute（重算）**两条路，论文 §7.3 的对比结论是小块重算更优、大块换出更优、中块相当，并称重算开销从不超过换出延迟的 20%；V0 时代两者都保留；**V1 移除了 swap、也没有写时复制 COW**（满块不可变 + 只追加，细节属于[《PagedAttention》第 4 节](/blog/pagedattention-给kv-cache装上虚拟内存/)），所以今天的抢占**只有重算一条路**：把已生成的词拼回原 prompt，一次 Prefill 就能重建全部 KV。

重算的边界也要说：单个事件确实不贵，被释放的块若哈希还在，重新 Prefill 时还能命中前缀缓存、更便宜；但**抢占一旦形成风暴，重算会叠加成秒级尖刺**——监控里 num_preemptions 持续上涨就是容量在 thrashing，该扩容，而不是继续调参。

## 7. 治什么、不治什么，以及收束

先把每类机制对应到指标上，口径写清：

| 机制 | 直接效果 | 治的指标 |
| --- | --- | --- |
| 请求每步动态进出 | 消除请求完成后的槽位空转 | 服务端聚合吞吐（tokens/s） |
| Decode 拼批摊薄权重 | 每 token 成本随人数下降 | 单卡并发容量 |
| Chunked Prefill | 长 prompt 不再独占多站 | TBT 分位（P99 尖刺有界）、尾延迟约束下的 goodput——**不承诺裸吞吐提升** |

真遇到线上症状，按这张表选旋钮：

| 症状 | 对应动作 |
| --- | --- |
| TBT 周期性鼓包，且和长 prompt 出现的时间同步 | 调小 chunk 预算 |
| 在批序列数到顶（达到 max_num_seqs）但 KV 块还有空 | 调大 max_num_seqs |
| num_preemptions 持续上涨 | 扩容，这是 thrashing 不是调参问题 |
| chunk 已压很小，高负载下尾延迟仍然被打爆 | 上 PD 分离 |

<Expand title="展开：指标口径的几个易混点">

- vLLM 的 TTFT 直方图**从请求到达时刻算起、包含排队时间**：轻载时它约等于 Prefill 耗时，过载时升高是**容量信号、不是模型变慢**；排队时间另有独立的 queue_time 指标。
- TBT（vLLM 指标里叫 ITL）是逐 token 间隔采样：抢占造成的大段空缺**不产生 TBT 样本**，判断稳态干扰看 TBT 的 P99、判断抖动事件要看端到端时间和 preempted 计数，两者不能互替；TBT 一律看分位，不看均值。
- 多个服务进程（DP、多 API 实例）下，token 计数要**求和**不是平均；服务端 tokens/s 与客户端体感 tok/s 之间还差着网络和客户端排队。
- 文献里 goodput 的口径（沿用 DistServe 约定）：TTFT 和 TBT 两个延迟目标**同时满足**时的请求速率；「裸吞吐最高」和「goodput 最高」的配置可能完全不同。TBT、ITL 是同一个东西，TPOT 则是 DistServe 按输出 token 数归一化的口径，引用时留意。

</Expand>

显式边界也列三条：**batch=1 或流量很轻**时没有摊薄对象，连续批处理不带来收益；**纯离线大批量 Prefill** 场景，切块反而拆碎计算效率；**客户端测出的延迟含排队时间**，别算成「模型变慢」。如果高干扰在线混部下，只靠混批调度已经压不住干扰——那就是下游[《PD 分离》](/blog/pd分离-把prefill和decode拆开部署/)的场景：同一个心跳问题的两个答案，chunk 让尖刺有界但不为零，PD 干脆把共用节拍器拆成两个（代价是约 2 倍实例资源、依赖 RDMA 网络，且在 0.21/0.29 官方仍标注 experimental、原话不提升裸吞吐）。同批机制相关的还有[投机解码](/blog/投机解码-小模型打草稿大模型一次批改/)（draft token 也走同一套批次计量）和自动前缀缓存 APC（减少 Prefill 工作量，见[《PagedAttention》第 4.3 节](/blog/pagedattention-给kv-cache装上虚拟内存/)）。想往深里走，vLLM 中文源码系列的[《调度与 KV Cache》](/inference/)讲的就是本文这套机制的代码实现。

最后回头重算开头那笔账：静态批处理下 800 个槽位·步、430 有效、370 空转。**连续批处理把这 370 个空槽位变成「完成即释放、空出即可准入」的可复用容量**；剩余空槽只来自两种情况——没有请求到达（轻载），以及准入策略保守（第 6 节的闸门）。

## 8. 常见误解

- **「连续批处理就是把 batch 调大」**——不是。核心是每个迭代步重新计算成员；一个从不变动的大 batch，照样按最长请求空转。
- **「开了 Chunked Prefill 吞吐更高」**——典型情况下它用少量裸吞吐和新请求的 TTFT，换 TBT 稳定和尾延迟约束下的服务容量。
- **「被抢占 = 进度保存，等会儿接着算」**——V1 里是释放全部 KV、进度归零、排队重算，不是存档续算。
- **「Orca 是 vLLM 的一部分 / Orca 有 arXiv 号」**——Orca 是 OSDI'22 的独立系统、没有 arXiv 预印本；「连续批处理」是业界后来叫开的名字。
- **「请求一到就能进 running」**——先通过按完整输入长度估算的准入检查。
- **「现在装 vLLM 就能拿到 Sarathi 的 10 倍」**——V1 早已内置该机制，那是 2023 年对照旧基线的历史增量。

## 9. 自测（答案点击展开）

**1.** 静态批处理的两笔浪费分别是什么？

**2.** Orca 2022 年定义的 selective batching，「选择」的是什么？今天这条边界为什么基本消失了？

**3.** 拼批隔离的两道关卡各管什么？为什么说因果掩码单独挡不住跨请求泄露？

**4.** 限制在批请求数的三个硬约束是什么？

**5.（数字题）** 用第 3 节的假设，手算 $B=8$ 那一行：单步耗时和每人每 token 成本各是多少？

**6.（加分辨析）** 监控显示：TBT 每隔十几秒出现一次约 300ms 的鼓包，时间点和用户提交长文档吻合，num_preemptions 几乎为零。该调哪个旋钮？如果同时还看到 num_preemptions 持续上涨、P99 TBT 打满，处置有什么不同？

<Expand title="参考答案">

1. ① 请求陆续完成后无法退出，槽位空转（玩具例中 370/800 = 46%）；② 批次封死期间，新请求无法加入、只能排队等待。
2. 「选择」的是只把投影、FFN、LayerNorm 等带权重算子展平拼批，注意力当时因不挂参数、各请求长度不一一而逐请求单独执行。今天变长 / Paged 注意力内核成熟，注意力也能按请求边界拼批，这条历史边界在现代引擎里基本消失。
3. 请求边界（Orca 的 Split、现代内核的 cu_seqlens、显式 batch 维）负责**跨请求隔离、防泄露**；因果掩码只在每个请求**段内**生效，保证并行结果与串行等价。拼批序列里 token 全局编号，因果掩码允许位置靠后的 query 看到位置更早的 token——包括其他请求的，所以它单独挡不住跨请求泄露。
4. KV 容量（物理块总数）、max_num_seqs（在批序列数上限）、TBT 预算（单步时长随请求数缓慢变长，延迟约束先到）。
5. 搬运量 = 140 + 8×0.64 = 145.1GB；单步 = 145.1 ÷ 3.35 ≈ 43.3ms；每人每 token = 43.3 ÷ 8 ≈ 5.4ms。
6. 前半问：鼓包与长 prompt 同步、且没有抢占，是长 Prefill 占站的典型症状——**调小 chunk 预算**（并可结合长 prompt 的 TTFT 要求权衡）。加分辨析：若 num_preemptions 持续上涨同时 P99 打满，说明是**容量 thrashing**，调参无效，该扩容；若高负载下 chunk 已压很小尾延迟仍被干扰打爆，则问题在 Prefill/Decode 混部本身，该评估 **PD 分离**而不是继续拧 chunk 旋钮。

</Expand>
