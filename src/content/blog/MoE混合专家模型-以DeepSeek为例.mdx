DeepSeek-V3 有 **6710 亿（671B）参数**，但每个 token 实际参与计算的只有约 **370 亿**（37B）——这不是量化、也不是剪枝，而是 **MoE**（Mixture of Experts，混合专家模型）。它把"模型有多大"和"每个 token 算多少"**解耦**了：模型可以巨大，但每个 token 只走其中一小部分。DeepSeek-R1 同样是 MoE 架构。这篇讲清 MoE 的原理、DeepSeek 的关键创新，以及一个反直觉的工程现实。

## 1. MoE 是什么：把 FFN 换成一排"专家"

回顾 Transformer 结构（见[图解 Transformer](/llm/)）：每个 Block 里有两个核心子层——注意力 + **FFN/MLP**（前馈网络）。其中 **FFN 是参数大头**（约占参数量 2/3），它更像模型的"知识存储"。

**MoE 的做法**：不再用 1 个大 FFN，而是放 **N 个小 FFN**（叫"专家" expert），再加一个**路由器**（gating / router）决定每个 token 该交给哪几个专家处理：

- **注意力层不变**（所有 token 共享）；
- **FFN 层变成 MoE 层**：N 个专家 + 1 个路由器；
- 每个 token 只被**权重最高的 K 个专家**处理（K 很小，如 1 或 2），其余专家完全不参与。

<MoeFigure />

*图 1：一个 token 经过路由器打分，只激活 N 个专家中的 Top-K（示意 K=2），其余专家这一步完全不计算。*

**数学上**：路由器先给每个专家打分（softmax 归一化），选出 Top-K，再对这几个专家的输出**按门控权重加权求和**：

$$
g(x)=\mathrm{TopK}\big(\mathrm{softmax}(u(x))\big),\qquad y=\sum_{i\in \mathrm{TopK}} g_i(x)\cdot E_i(x)
$$

其中 $E_i(x)$ 是第 $i$ 个专家（一个小 FFN），$g_i(x)$ 是路由器给它的权重；不在 Top-K 里的专家权重为 0、**完全不算**。

> **Top-1 vs Top-2**：早期 Switch Transformer 用 Top-1（只走 1 个专家，更省）；Mixtral 8x7B 用 Top-2（每个 token 走 2 个专家，效果更稳）。

这样，**总参数量 ≈ N 个专家之和（巨大），但每步计算量 ≈ K 个专家（很小）**——这正是"大模型、小计算"的关键。

## 2. 发展时间线：DeepSeek 站在谁的肩膀上

MoE 不是 DeepSeek 发明的，它有一条清晰的演进线：

| 年份 | 工作 | 关键贡献 |
| --- | --- | --- |
| 2017 | **Shazeer《Sparsely-Gated MoE》** | 现代稀疏 MoE 源头：引入门控网络 + Top-K，首次大规模实践 |
| 2020 | **GShard**（Google） | Top-2 门控、上千专家、把 MoE 扩展到超大规模分布式 |
| 2021 | **Switch Transformer**（Google） | 简化为 **Top-1**，通信/计算更省，推动稀疏效率 |
| 2022 | **ST-MoE / GLaM** | 路由稳定性、专家负载均衡的改进 |
| 2023 | **Mixtral 8x7B**（Mistral） | 开源引爆点：8 个专家、每 token 选 2，用很小的激活量达到更大模型的能力 |
| 2024 | **DeepSeekMoE / DeepSeek-V2** | **细粒度专家分割 + 共享专家**，负载均衡去掉辅助损失 |
| 2024–2025 | **DeepSeek-V3 / R1** | 671B 总参 / 37B 激活，集大成 |

可以看到两条贯穿始终的演进目标：**① 让专家分工更细、更专业；② 让专家之间的负载更均衡**。DeepSeek 的创新正是沿着这两条线。

## 3. 核心难题：负载均衡（DeepSeek 创新的铺垫）

MoE 最大的训练痛点是**负载不均衡**（load imbalance）：

- 路由器自己学出来后，容易出现**赢者通吃**——少数专家被反复选中、越来越强，多数专家几乎拿不到 token、逐渐"荒废"；
- 这是个正反馈循环：选得多的专家训练得更好，训练得好又更容易被选中。

**传统解法：辅助损失**（auxiliary loss）。给训练目标加一项"鼓励各专家被均匀使用"的惩罚项：哪个专家过载就降低它被选中的概率。但它有副作用——

<Expand title="扩展阅读：辅助损失为什么有副作用、DeepSeek 怎么解">

辅助损失在数学上鼓励"平均分配 token"，但这和语言建模的真正目标（**让最合适的专家处理 token**）并不总是一致：为了均衡，可能强行把 token 分给不那么匹配的专家，反而**轻微损害模型能力**。

**DeepSeekMoE 的破法**（aux-loss-free balance，无辅助损失均衡）：

- 给每个专家一个**动态偏置项** $b_i$，作用于门控打分：某专家**当前负载超过阈值就降低它的偏置**（让它暂时更难被选中），负载低就提高偏置；
- 这个调整**直接作用在门控分数上**（在 softmax 之前），而**不是加一个和语言目标冲突的额外损失**；
- 再配合**互补序列融合**（complementary sequence-wise）等技术，把不同专家负载在 batch 维度互补地拉平。

效果：既保证了负载均衡、又不牺牲专家匹配质量——这是 DeepSeekMoE 论文的核心贡献之一。

</Expand>

一句话：**旧办法用"额外惩罚"逼均衡（有伤效果），DeepSeek 直接在路由打分时动态调节（不伤效果）**。

## 4. DeepSeekMoE 的两大结构创新

### 4.1 细粒度专家分割（fine-grained segmentation）

直觉上，专家切得**越大，单个专家要干的事越杂**；切得**更小更多**，每个专家就能更专注、组合也更灵活。DeepSeek 把专家切成**更细的粒度**：不是"8 个大专家选 2"，而是"**几十个小专家，每个 token 从中选更多个**（如 8 个）"。

- 细专家更**专业化**，被选中时分工更精准；
- 激活的组合更多样，能覆盖的功能更全。

### 4.2 共享专家（shared expert）

另一个观察是：有一部分知识是**几乎所有 token 都需要的**（通用语法、常见模式）。把它们也交给路由器选择是浪费。DeepSeek 因此设置了 **K_s 个共享专家**（shared expert）——它们**始终激活、每个 token 都走**（不经过路由）；其余是**路由专家**（routed expert），仍按 Top-K 选择。

<DeepseekMoeFigure />

*图 2：DeepSeekMoE = 1 个始终激活的**共享专家**（承接通用知识、稳定路由）+ 一排细粒度**路由专家**（每个 token 选 Top-8，绿色为本次激活）。*

共享专家的好处：把"通用"和"专用"分开——共享专家兜住通用计算，路由专家专注差异化知识，**既提升效果又让路由更稳定**。

### 4.3 数字：大模型、小计算

以 **DeepSeek-V3** 为例（注意和早期 DeepSeekMoE 实验模型区分）：

- **总参数约 671B**，但每个 token **激活约 37B**（约占 5.5%）；
- MoE 层共 **256 个路由专家，每 token 激活 8 个**，另有 **1 个共享专家**；
- 训练用 **FP8** 等技术进一步压成本。

这意味着：模型"身材"有 6710 亿（知识容量巨大），但每步推理只动用 370 亿的算力——**效果对标超大稠密模型，成本却接近中小模型**。

## 5. 工程现实：MoE 省算力，不省显存

这是最容易误解的一点，必须讲清楚：

<Expand title="关键澄清：MoE 省的是 FLOPs，不是显存">

- **省计算**（FLOPs/速度/训练成本）：每个 token 只过 K 个专家，算得少、训练快；
- **不省显存**：虽然每次只激活一部分，但**所有专家的权重都要常驻显存/内存**才能被随时路由到。所以一个 671B 的 MoE，推理时仍需加载约 671B 参数的权重（量化后也要几百 GB 级别显存），这也是为什么 DeepSeek 大 MoE 主要跑在**多卡/云端**。

对比：**量化**（见[大模型量化](/blog/大模型量化-用更少的显存跑更大的模型/)）是把每个权重压到 INT4/FP8，省的是**存储和带宽**；**MoE** 省的是**每 token 的计算量**。两者正交，可叠加。

</Expand>

**MoE 推理的额外难点**（专家并行 EP）：

- 专家太多放不下一张卡，要把不同专家**分到不同 GPU**（Expert Parallelism）；
- token 被路由到不同专家，引发跨卡 **all-to-all 通信**；
- 负载不均会导致有的卡空转、有的卡排队，产生**延迟抖动**。
- 这些都是 vLLM 等推理引擎在 MoE 部署上要专门调度的工程问题（见[推理加速实战](/inference/)）。

### DeepSeek 的"三件套"如何协同

DeepSeek 大模型把三套省成本机制叠在一起，各管一块：

<DeepseekStackFigure />

*图 3：**MoE** 省 FFN 层的计算量、**MLA** 省注意力的 KV Cache（见[注意力机制演进](/blog/注意力机制演进-从mha到gqa与mla/)）、**FP8** 省训练算力与显存带宽。*

- **MoE**：FFN 层稀疏激活，省**计算**（37B/671B）；
- **MLA**：注意力的 K/V 压成低秩潜变量缓存，省 **KV Cache**；
- **FP8 训练**：权重/激活用 8-bit 浮点，省**训练算力和带宽**。

三者作用在不同部分、互不冲突，共同让一个 671B 模型的训练和推理成本变得可承受。

## 6. 全景对比与选型

| 维度 | Dense（稠密） | MoE（混合专家） |
| --- | --- | --- |
| 总参数 vs 激活参数 | 全部激活（相等） | **总参数巨大、激活很少**（解耦） |
| 训练成本 | 随参数线性增长 | 相同算力可训出大得多的模型 |
| 推理显存 | 只加载"激活大小"的权重 | **要加载全部专家权重**（显存大） |
| 推理 FLOPs | 全模型 | 只算 Top-K 专家，**每 token 更快** |
| 主要难题 | 容量受限 | 负载均衡、专家并行/通信、部署复杂 |
| 适合场景 | 端侧 / 中小模型 / 简单部署 | **云端超大规模、追求性价比** |
| 代表模型 | LLaMA、Qwen（dense 版） | **DeepSeek-V3/R1、Mixtral、Qwen-MoE、GPT-4**（业界普遍认为是 MoE） |

**一句话**：云端想拿"大模型能力"又要"可接受的训练/推理算力" → MoE 非常划算；端侧/边缘、追求部署简单和小显存 → 稠密模型更合适（MoE 全部专家要常驻，显存不友好）。国产模型里，DeepSeek 把 **MoE + MLA + FP8 + 辅助损失-自由均衡** 组合成了一套高性价比方案，是当前工程实践的代表。

## 自测（答案点击展开）

**Q1. 常听到"DeepSeek-V3 是 671B 的大模型"，为什么又说"每 token 只激活 37B"？MoE 让模型变小了吗？**

<Expand title="查看答案">

模型没有变小——**总参数仍是 671B**（这些权重都存在、推理时都要加载进显存）。"37B"指的是**每个 token 实际参与计算的参数**（激活参数）：MoE 中每个 token 只经过选中的 Top-K 个专家（约 37B），其余专家这一步不计算。
- **671B 决定知识容量和显存占用**；
- **37B 决定每步计算量**（FLOPs/速度）。
MoE 把"模型多大"和"每 token 算多少"解耦了，所以效果像超大模型、计算却像中小模型。

</Expand>

**Q2. MoE 省显存吗？为什么 DeepSeek 671B 这种大 MoE 主要跑在云端多卡？**

<Expand title="查看答案">

**MoE 省的是计算量，不省显存。** 尽管每个 token 只激活少数专家，但所有专家的权重都必须常驻显存（随时可能被路由到），所以推理仍需装下约 671B 的参数（量化后也需大量显存）。因此大 MoE 要用**专家并行**（EP）把专家分布到多张 GPU 上，还会产生跨卡 all-to-all 通信和负载不均的延迟问题。这决定了大 MoE 主要部署在云端多卡，而端侧更常用显存友好的稠密模型或 MoE+量化。

</Expand>

**Q3. DeepSeekMoE 相比传统 MoE 做了哪两个结构改进？"共享专家"解决了什么问题？**

<Expand title="查看答案">

两个结构改进：
1. **细粒度专家分割**：把专家切得更小、更多，每个 token 从大量细专家中选更多个（如 256 选 8），让专家更专业化、组合更灵活；
2. **共享专家**（shared expert）：设置少量**始终激活**、不经路由的专家，专门承接所有 token 都需要的通用知识。

共享专家解决的问题：通用知识若也交给路由，会造成重复选择/浪费和路由不稳定；让共享专家兜底通用计算，路由专家专注差异化、专业化的知识，既提升效果又稳定路由。此外 DeepSeek 还用**无辅助损失的负载均衡**（直接在门控打分上动态调节专家偏置）替代会伤效果的辅助损失。

</Expand>
