在[《一次推理的旅程》](/blog/一次推理的旅程-Prefill与Decode/)里我们算过一笔账：70B 模型 FP16 权重约 140GB，一张 H100 的显存带宽约 3.35TB/s，Decode 阶段每生成一个词，光把权重从显存搬到芯片上就要约 **42ms**，而这一步真正的计算只占零头。

看着这 42ms 自然会冒出一个问题：**搬一趟权重只换来 1 个词，那能不能让这一趟同时换来 30 个词？** 全文就回答这一个问题——答案叫**连续批处理（Continuous Batching）**，它是今天所有高吞吐推理引擎的默认工作方式，也是 vLLM 调度器的灵魂。

| 迭代步 iteration | 引擎做一次模型前向，所有在跑的请求恰好各前进一个 token |

</Expand>

## 1. 先看旧规矩：一份「包车蠢合同」

要感受连续批处理好在哪，先看没有它时引擎怎么干活。

早期深度学习框架里，**一次函数调用就是一个固定形状的张量**：你交给它 4 个请求，这批数据从头到尾就是 4 行，中途不能有请求退出，也不能有请求加入。蠢的不是乘客也不是 GPU，是这份「合同」——请求们像包了一辆车，必须等**最远的乘客**跑完才能散场。

假设车上 4 个请求，各自要生成 50、80、100、200 个词。我们用「座位·步」记账（一个座位·步 = 一个请求在一个迭代步里占的位置）：

| 步区间 | 在岗人数 | 空座·步 |
| --- | --- | --- |
| 1–50 | 4 | 0 |
| 51–80 | 3 | 30 |
| 81–100 | 2 | 40 |
| 101–200 | 1 | 300 |

自己加一下：这辆车总共卖出 200 × 4 = 800 个座位·步，真实产出只有 50+80+100+200 = 430，**空转 370 个，占 46%**；而且其中 300/370 集中在最后一段——请求陆续干完，坐在车上等最远的那个。

<CbStaticPainFigure />

*图 1：静态批处理按最远的人计费——蓝色是真实产出，斜纹是干完后干坐；新来的请求只能在车外。*

第二笔浪费藏在时间轴下面：**这 200 步里到达的新请求，只能站在车外干等**，一个都上不来。

这笔账有几个玩具假设要交代清楚：四个请求同时出发、每个迭代步墙钟等长、每请求每步恰好占一个座位、中途没有来客、也没算旧框架对输入做左 padding 的额外浪费。还要提前防一个过度解读：**真实流量到达稀疏时，任何机制的车上都有空座**——46% 是这个玩具模型的上界，真实收益由请求的到达分布和输出长度分布决定。

那合同能不能改？能。下一节看新规矩。

## 2. 新规矩：公交车每站关门，重新点名

新规矩一句话：**不凑整车，每一站都重新组一批。**

公交车每跑一站，芯片恰好做一次模型前向——这个「站」在术语里叫一个**迭代步（iteration）**。每次关门前司机点名：这站谁还在跑？刚生成完的请求，**这一站就下车**；站台上等着的请求，只要有座，**这一站就上车**。

> 意象上做个桥接：[《PagedAttention》](/blog/PagedAttention-给KV-Cache装上虚拟内存/)那篇我们用「每一层都能进人的电梯」形容过它，本篇要算清每站的账，换成站站停的公交车；上一篇里「等全员到齐的班车」这里改叫包车——同一个笨蛋，两个名字。

<CbRosterFigure />

*图 2：第 1 站批次为 A、B；一个迭代步后，B 完成下车、C 在站台有座上车，第 2 站变成 A、C。*

注意图 2 教的是强版本：**下车和上车在两次关门之间同时完成**，不是先等谁下车、再等谁上车。请求的生命周期因此变成：到达后进 waiting 集合 → 被点名上车进 running → 每站前进一个 token → 完成即离场。调度器手上就是三个集合：站台上的 waiting、车上的 running、这一站刚散场的 finished；每站固定三段——schedule() 点名、执行一次前向、update_from_output() 记账。

这套机制出自 **Orca**（Yu et al.，OSDI 2022），论文里的正式名字是 **iteration-level scheduling**（迭代级调度）；「continuous batching 连续批处理」是 2023 年业界叫开的名字——Anyscale 当年在 continuous / dynamic / iteration-level 三个近义词里选定了 continuous batching。顺带注意别和微软的 Orca *模型*论文搞混，两篇同名但毫无关系。

### 拼车为什么不出事：两道关卡分工不同

不同请求拼在一个迭代步里，最自然的担心是「它们会不会互相看到对方的内容」。安全靠两道分工不同的关卡：

1. **请求边界防串车。** 不同请求之间必须有明确边界：Orca 的做法是在注意力之前 Split（拆开），每个请求单独算注意力；现代融合内核则把 cu_seqlens——记录各请求 token 区间起止位置的索引数组，相当于块对角边界——喂给内核；如果用显式的 batch 维度，每一行天然就是隔离的。
2. **因果掩码防看未来。** 它只在**每个请求自己的序列内部**生效：保证位置 $i$ 只看得到 $\le i$ 的内容，让「拼起来并行算」和「一个请求一个请求串行算」结果完全等价。因果掩码单独**管不了「不看别的请求」**——拼车序列里 token 位置全局编号，靠前的其他请求 token 它恰恰是允许看到的，隔开请求的是第 1 道关卡。

这个口径和[《一次推理的旅程》第 2.1 节](/blog/一次推理的旅程-Prefill与Decode/)完全一致：掩码是「并行结果与串行等价」的保证，不是跨请求隔离的手段。

### Selective Batching：「能拼才拼」的原始定义

Orca 还配套了一项执行层技术，叫 **selective batching（选择性批处理）**。2022 年的原始定义要按历史讲：投影、FFN、LayerNorm 这些**带模型权重**的算子，把多个请求的 token 展平成张量拼批计算；**注意力当时反而要拆开、每个请求单独执行**——论文给出的理由是注意力不挂参数，拼批得不到「摊薄权重搬运」的收益，而各请求长度不一，拼起来还麻烦。

今天变长注意力内核（FlashAttention varlen、PagedAttention kernel）已经成熟，注意力也能按请求边界拼车，这条历史边界在现代引擎里基本消失了。所以别把它当成当前 vLLM 的行为描述——它是 2022 年的工程约束。

公交车这个类比也有几条不成立的边界，提前划清：

- 这辆车**没有站票**：座位数等于 KV 显存容量，绝不能超载；
- 每站所有乘客恰好前进一个 token（齐步走 lockstep），不是连续平滑移动；
- 车不等人，这站没上来就等下一站；
- 每站的停靠时间随乘客数和行李大小变化——这就是 TBT，不是固定值；
- 上车前先验票（第 6 节的准入闸门）；
- 真实公交车不会把乘客赶下车——抢占是第 6 节的「非正常操作」。

<Expand title="展开：V1 引擎里队列与策略的实现细节">

- 调度器内部实际有 **waiting、skipped_waiting、step_skipped_waiting** 三个等待队列加一个 running 列表：被异步依赖卡住的请求（等远程 KV、等结构化输出语法编译、等流式输入）先放进 skipped；每步新跳过的请求收集在 step_skipped 里，调度结束后插到 skipped **前面**，保证新跳过的比旧跳过的先重试。
- 调度策略两种：**FCFS**（先到先服务，默认）和 **priority**（按优先级，值越小越优先，平局看到达时间）。
- running 是一个**列表**而不是队列：FCFS 抢占时直接弹出最后一个；priority 抢占时挑优先级最低的。
- 一条关键纪律：**某个迭代步一旦发生抢占，这一步就不接纳新请求**——先让被踢的请求重新 Prefill，防止它饥饿。

</Expand>

机制清楚了，但「为什么值得这么折腾」的经济账还没算。下一节用开头的 42ms 算给你看。

## 3. 经济账：权重搬一趟，全批人共享

Decode 是显存带宽受限的：一个迭代步里，**模型权重只需要搬一遍，同批 $B$ 个请求共享这一趟**。用开头的数字算（70B 抽象设备 / TP 聚合口径，每人按 2K 上下文、KV 约 0.64GB，忽略计算与开销）：

| 同车人数 $B$ | 搬运总量 $W + B\times\text{KV}$ | 单步耗时（÷3.35TB/s） | 每人每 token |
| --- | --- | --- | --- |
| 1 | 140.6 GB | 42.0 ms | 42 ms |
| 8 | 145.1 GB | 43.3 ms | 5.4 ms |
| 32 | 160.5 GB | 47.9 ms | 1.5 ms |

你可以手算中间那行验证：(140 + 8×0.64) ÷ 3.35 ≈ 43.3ms，每人成本 43.3 ÷ 8 ≈ 5.4ms。**单步只慢了一点点，每人每 token 的成本掉了一个数量级。**

<CbCostFigure />

*图 3：堆叠柱——权重段每步固定 140GB，KV 段随人数增长；绿色虚线是每人每 token 成本（示意，非实测）。*

用符号收口，先命名：$W$ 为权重字节、$B$ 为同车人数、每人 KV 为该请求的全量历史 KV：

$$
\text{单步耗时}\approx \frac{W + B\times\text{每人 KV}}{\text{显存带宽}}，\qquad \text{每人每 token}\approx \frac{W}{B}+\text{每人 KV}
$$

这里 KV 的口径必须钉死：它是该请求**当前全部历史的 KV**（约等于上下文长度 × 每 token KV），Decode 每一步都要从显存重新读一遍、随上下文长度线性增长——不是「一个新 token 的 KV」。这也解释了表里看似矛盾的两列：**每人成本随 $B$ 下降**（$W/B$ 项变小），**单步总时长随 $B$ 缓慢增加**（$B\times\text{KV}$ 项变大），说的是同一件事的两面。

$B$ 能不能无限大？三把刹车：

1. **KV 容量**：每个请求的 KV 都要占物理块，块总数是硬上限（见[《PagedAttention》](/blog/PagedAttention-给KV-Cache装上虚拟内存/)）；
2. **max_num_seqs**：引擎对同车人数有配置上限，限制内核形状与调度开销；
3. **TBT 预算**：$B$ 增大时单步总时长缓慢变长，通常在撞到前两把刹车之前，延迟约束先到。

经济账到此成立。但如果上车的不只是 Decode，还有一个几千 token 的长 prompt 呢？

## 4. 病理：长 prompt 一个人占住全车的站

回忆 Prefill 和 Decode 的差别：Prefill 一次处理成百上千个 token，是**算力受限**的，一个迭代步装不下；Decode 每步只算一个 token，是**带宽受限**的。

如果引擎不做分块，长 prompt 就得**连续占用多个迭代步**把 Prefill 算完。问题的因果要钉准：**不是「长 prompt 算得慢」，而是「它占住了这一站，而每一站是全批共用的」**——这几站里，车上所有 Decode 请求一步都推进不了，TBT 出现数百 ms 量级的尖刺，等待队列里其他请求的 TTFT 也一起堆高。

<CbStallFigure />

*图 4：长 prompt 的 Prefill 连续占第 1–3 站，三排 Decode 零推进，第 4 站才恢复蹦字。*

这个「共用节拍器」的比喻，在[《PD 分离》第 1 节](/blog/PD分离-把Prefill和Decode拆开部署/)里用心跳和深呼吸讲过：Decode 是约 20ms 一次的心跳，Prefill 是数百 ms 的深呼吸——这里的「数百 ms」是量级示意，随模型与硬件变化，对应的是关闭分块的旧引擎。

论文证据只留最小的一组。**Sarathi**（2023 预印本）最早系统地研究了这个问题：在 LLaMA-13B/A6000 上，让 Decode 搭车 Prefill 块的**边际成本**比 Decode-only 迭代低 **2.8–10 倍**——10 倍是小 batch、短序列下的上界（微观上是 1.2ms vs 12.49ms/token），而**端到端吞吐最高只提升 1.33 倍**。两个提醒缺一不可：这是 Decode 的**边际**吞吐、不是系统总吞吐；当前 V1 引擎已经内置了这套机制，这些数字代表 2023 年的历史空间，不代表今天升级 vLLM 还能拿到。后续的 **Sarathi-Serve**（OSDI 2024）把它做成「无停顿调度」：在尾延迟目标约束下，Mistral-7B/单 A100 的服务容量提升 2.6 倍（基线为 vLLM；服务容量即达 SLO 的有效吞吐 goodput，不是裸吞吐）。

<Expand title="展开：论文证据全表与实验条件">

| 实验 | 配置 | 结果 | 口径 |
| --- | --- | --- | --- |
| Sarathi | LLaMA-13B / A6000 | Decode 边际 2.8–10×；端到端最高 1.33× | 端到端峰值条件：$B=6$、序列长 1K、Prefill:Decode=50:1 |

怎么让「深呼吸」不把心跳憋停？下一节就是答案。

## 5. Chunked Prefill：大件行李分次上车

先上一个留在公交车域内的类比：一位带了 2000 件行李的乘客，一次搬完要占 3 站停靠时间，全车人关在车里等；新规矩是**每站最多帮他搬 512 件，4 站搬完**——每站其他人照常前进。他落座的时刻变晚（TTFT），但每站的停靠时长（TBT）从此有了上界。

机制上，长 prompt 被切成定长的 chunk，每个迭代步的批次 = 全部 Decode 请求 + 当步恰好完整完成的短 prompt + **至多 1 个**未完成的 Prefill 块。两个旋钮别搞混：每站「搬多少件」由 token 预算（max_num_batched_tokens）控制；默认配置下「每步至多一个未完成块」其实是 **FCFS 加预算分配自然保证的**——0.21 的核心调度器并不直接读取 `max_num_partial_prefills`（该字段仅在 ROCm AITER 后端被用于 CUDA graph 定尺寸；细节与全部旋钮的消费方核查见 [《Chunked Prefill》第 8 节](/blog/ChunkedPrefill-把长Prompt切成节拍器能消化的小块/)）。还有一条优先级纪律：**Decode 优先**——每步先喂 running 的请求，Prefill 块只吃剩下的预算，保证 Decode 不会被饿死。

<CbChunkFigure />

*图 5：长 prompt 切成 4 块、每站一块与 Decode 并排；绿色虚线处才是它的首字 TTFT。*

这个机制不是免费午餐，三条代价必须写明：

1. **长 prompt 的 TTFT 被拉长**：它的 Prefill 要分多个站、每站只能拿到剩余预算；
2. **裸吞吐可能略降**：分块拼内核的总效率略低于大块一次算完——换来的是 TBT 稳定和尾延迟约束下的服务容量提升，不是"开了就更快"；
3. **预算是延迟/吞吐旋钮**：预算调大，长 prompt 完成得快但 Decode 被挤占得多；调小则反过来。

<Expand title="展开：V1 的 token 预算默认值（0.21 / 0.29 快照）">

vLLM 0.21（2026-05）在无人为覆盖时，按硬件分档（判定条件原文：**显存 ≥70GiB 且设备名不含 "a100"** 才走大档）：

| 硬件档 | API 服务（tokens / seqs） | 离线批量（tokens / seqs） |
| --- | --- | --- |
| A100 及其他小显存档（＜70GB） | 2048 / 256 | 8192 / 256 |
| H100/H200/MI300x（≥70GB，A100 除外） | 8192 / 1024 | 16384 / 1024 |

0.29（发稿时最新版，2026-09-09）新增一档：显存 **≥160GB**（B200/B300 类）时，**API 服务也是 16384 / 1024**。

- Chunked Prefill 与上面的分档预算在 V1 中**默认开启**。
- A100 上盲目调大预算反而降吞吐：PR #17885 的实测是 Llama-3.1-70B **TP=2 时小预算 +36%、TP=4 时约 −2%（基本中性）**，测试条件为请求灌满的吞吐测试。结论不是"A100 必须调小"，而是方向随硬件代际 × 并行度 × 在线/离线而变，上线要按自己的负载复测。
- 启动时加 `--performance-mode throughput`，默认预算和座位数会**翻倍**（仅对未显式覆盖的值生效）。
- 以上均为版本快照（2026-09，以官方文档为准）。

</Expand>

每站预算还有一个更硬的约束：座位是有限的。座位不够时怎么办？

## 6. 座位不够：准入闸门与抢占

第一道防线在门口：**酒店前台先确认全团都住得下，才给登记**。新请求上车前，引擎按它的**完整输入长度**（ISL，Input Sequence Length，即 prompt）估算需要多少 KV 块、能不能装下——不是只算第一块——装不下就留在 waiting。对应配置 `scheduler_reserve_full_isl`，V1 默认开启，为的是防止分块 Prefill「先上车后翻车」造成 KV 显存抖动。注意这是**可行性估算、不是物理预留**：过了闸门的请求，之后照样可能被抢占。

第二道防线在车上：**某个 running 请求在下一站的 KV 块分配失败时**（再次强调：不是新客抢座），触发抢占：

- FCFS（先到先服务）策略下，踢**最后上车的人**（LIFO，后进先出），保护更早到达的请求——顺带点破：刚上车的新请求正是头号被踢对象；
- priority 策略下，踢优先级最低的请求；
- 被踢的请求**释放全部 KV、进度归零**，回到 waiting 队首优先重新 Prefill。

<CbPreemptFigure />

*图 6：请求视角的抢占旅程——running → 踢下 → waiting 队首 → 重新 Prefill → 重新 running。*

按时间戳区分三代机制，别混用：vLLM 论文（2023）里有 **swap（把 KV 换出到 CPU 内存）和 recompute（重算）**两条路，论文 §7.3 的对比结论是小块重算更优、大块换出更优、中块相当，并称重算开销从不超过换出延迟的 20%；V0 时代两者都保留；**V1 移除了 swap、也没有写时复制 COW**（满块不可变 + 只追加，细节属于[《PagedAttention》第 4 节](/blog/PagedAttention-给KV-Cache装上虚拟内存/)），所以今天的抢占**只有重算一条路**：把已生成的词拼回原 prompt，一次 Prefill 就能重建全部 KV。

重算的边界也要说：单个事件确实不贵，被释放的块若哈希还在，重新 Prefill 时还能命中前缀缓存、更便宜；但**抢占一旦形成风暴，重算会叠加成秒级尖刺**——监控里 num_preemptions 持续上涨就是容量在 thrashing，该扩容，而不是调参数。

## 7. 治什么、不治什么，以及收束

先把每类机制对应到指标上，口径写清：

| 机制 | 直接效果 | 治的指标 |
| --- | --- | --- |
| 请求每步动态进出 | 消除「干完干坐」的座位空转 | 服务端聚合吞吐（tokens/s） |
| Decode 拼车摊薄权重 | 每 token 成本随人数下降 | 单卡并发容量 |
| Chunked Prefill | 长 prompt 不再独占多站 | TBT 分位（P99 尖刺有界）、尾延迟约束下的 goodput——**不承诺裸吞吐提升** |

真遇到线上症状，按这张表选旋钮：

| 症状 | 对应动作 |
| --- | --- |
| TBT 周期性鼓包，且和长 prompt 出现的时间同步 | 调小 chunk 预算 |
| 座位到顶（人数撞 max_num_seqs）但 KV 块还有空 | 调大 max_num_seqs |
| num_preemptions 持续上涨 | 扩容，这是 thrashing 不是调参问题 |
| chunk 已压很小，高负载下尾延迟仍然被打爆 | 上 PD 分离 |

<Expand title="展开：指标口径的几个易混点">

- vLLM 的 TTFT 直方图**从请求到达时刻算起、包含排队时间**：轻载时它约等于 Prefill 耗时，过载时升高是**容量信号、不是模型变慢**；排队时间另有独立的 queue_time 指标。
- TBT（vLLM 指标里叫 ITL）是逐 token 间隔采样：抢占造成的大段空缺**不产生 TBT 样本**，判断稳态干扰看 TBT 的 P99、判断抖动事件要看端到端时间和 preempted 计数，两者不能互替；TBT 一律看分位，不看均值。
- 多个服务进程（DP、多 API 实例）下，token 计数要**求和**不是平均；服务端 tokens/s 与客户端体感 tok/s 之间还差着网络和客户端排队。
- 文献里 goodput 的口径（沿用 DistServe 约定）：TTFT 和 TBT 两个延迟目标**同时满足**时的请求速率；「裸吞吐最高」和「goodput 最高」的配置可能完全不同。TBT、ITL 是同一个东西，TPOT 则是 DistServe 按输出 token 数归一化的口径，引用时留意。

</Expand>

显式边界也列三条：**batch=1 或流量很轻**时没有摊薄对象，连续批处理不带来收益；**纯离线大批量 Prefill** 场景，切块反而拆碎计算效率；**客户端测出的延迟含排队时间**，别算成「模型变慢」。如果高干扰在线混部下，光靠同车调度已经拉不开干扰——那就是下游[《PD 分离》](/blog/PD分离-把Prefill和Decode拆开部署/)的场景：同一个心跳问题的两个答案，chunk 让尖刺有界但不为零，PD 干脆把共用节拍器拆成两个（代价是约 2 倍实例资源、依赖 RDMA 网络，且在 0.21/0.29 官方仍标注 experimental、原话不提升裸吞吐）。同车的邻居还有[投机解码](/blog/投机解码-小模型打草稿大模型一次批改/)（draft token 也走同一套批次记账）和自动前缀缓存 APC（减少 Prefill 工作量，见[《PagedAttention》第 4.3 节](/blog/PagedAttention-给KV-Cache装上虚拟内存/)）。想往深里走，vLLM 中文源码系列的[《调度与 KV Cache》](/inference/)讲的就是本文这套机制的代码实现。

最后回头重算开头那笔账：旧合同下 800 个座位·步、430 有效、370 空转。**连续批处理把这 370 个「后座」变成了「完成即下车、到站即上车」的随时可售座位**；车上剩下的空座，只来自两件事——没人来（轻载），和前台保守（准入闸门）。

## 8. 常见误解

- **「连续批处理就是把 batch 调大」**——不是。核心是每站重新计算成员；一个从不变动的大 batch，照样按最远的人空转。
- **「开了 Chunked Prefill 吞吐更高」**——典型情况下它用少量裸吞吐和新请求的 TTFT，换 TBT 稳定和尾延迟约束下的服务容量。
- **「被抢占 = 进度保存，等会儿接着算」**——V1 里是释放全部 KV、进度归零、排队重算，不是存档续算。
- **「Orca 是 vLLM 的一部分 / Orca 有 arXiv 号」**——Orca 是 OSDI'22 的独立系统、没有 arXiv 预印本；「连续批处理」是业界后来叫开的名字。
- **「请求一到就能上车」**——先过按完整输入长度估算的准入闸门。
- **「现在装 vLLM 就能拿到 Sarathi 的 10 倍」**——V1 早已内置该机制，那是 2023 年对照旧基线的历史增量。

## 9. 自测（答案点击展开）

**1.** 静态批处理的两笔浪费分别是什么？

**2.** Orca 2022 年定义的 selective batching，「选择」的是什么？今天这条边界为什么基本消失了？

**3.** 拼车安全的两道关卡各管什么？为什么说因果掩码单独挡不住跨请求泄露？

**4.** 限制同车人数的三把刹车是什么？

**5.（数字题）** 用第 3 节的假设，手算 $B=8$ 那一行：单步耗时和每人每 token 成本各是多少？

**6.（加分辨析）** 监控显示：TBT 每隔十几秒出现一次约 300ms 的鼓包，时间点和用户提交长文档吻合，num_preemptions 几乎为零。该调哪个旋钮？如果同时还看到 num_preemptions 持续上涨、P99 TBT 打满，处置有什么不同？

<Expand title="参考答案">

1. ① 请求陆续完成后不能下车，座位空转（玩具例中 370/800 = 46%）；② 批次封死期间，新请求上不来、在车外干等。
2. 「选择」的是只把投影、FFN、LayerNorm 等带权重算子展平拼批，注意力当时因不挂参数、各请求长度不一一而逐请求单独执行。今天变长 / Paged 注意力内核成熟，注意力也能按请求边界拼车，这条历史边界在现代引擎里基本消失。
3. 请求边界（Orca 的 Split、现代内核的 cu_seqlens、显式 batch 维）负责**跨请求隔离、防串车**；因果掩码只在每个请求**段内**生效，保证并行结果与串行等价。拼车序列里 token 全局编号，因果掩码允许位置靠后的 query 看到位置更早的 token——包括其他请求的，所以它单独挡不住跨请求泄露。
4. KV 容量（物理块总数）、max_num_seqs（座位上限）、TBT 预算（单步时长随人数缓慢变长，延迟约束先到）。
5. 搬运量 = 140 + 8×0.64 = 145.1GB；单步 = 145.1 ÷ 3.35 ≈ 43.3ms；每人每 token = 43.3 ÷ 8 ≈ 5.4ms。
6. 前半问：鼓包与长 prompt 同步、且没有抢占，是长 Prefill 占站的典型症状——**调小 chunk 预算**（并可结合长 prompt 的 TTFT 要求权衡）。加分辨析：若 num_preemptions 持续上涨同时 P99 打满，说明是**容量 thrashing**，调参无效，该扩容；若高负载下 chunk 已压很小尾延迟仍被干扰打爆，则问题在 Prefill/Decode 混部本身，该评估 **PD 分离**而不是继续拧 chunk 旋钮。

</Expand>
