## 1. 拍一：哈希增量长成链

引擎不给"任意长度前缀"建索引，只给**写满的块**算哈希，而且哈希沿链编码父块（kv_cache_utils.py:539）：

```python
def hash_block_tokens(hash_function, parent_block_hash,
                      curr_block_token_ids, extra_keys=None) -> BlockHash:
    ...
```

- 第一个块的 `parent_block_hash` 是 `NONE_HASH`；
- 后面每个块把**父块哈希 + 本块 token + extra_keys** 喂给哈希函数；
- 于是两个块的 token 相同还不够，**它们从开头起的全部前缀也必须相同**，哈希才相等。

这天然防住了一类误命中：同一批 token 出现在序列的不同位置（RoPE 让位置不同、KV 就不同），因为父哈希链不同，哈希必然不同。

*图 1：沿哈希链逐块比对，在第一个哈希不同的位置停下。*

`extra_keys` 把"除 token 外还会改变 KV 的因素"编进键，默认包含（kv_cache_utils.py:522-530）：LoRA 的 id、多模态输入标识与偏移、**只加在第一个块**的 `cache_salt`（多租户隔离）、prompt embeds 的哈希。注意一个易错点：KV group id **不在**请求的哈希链里，它只在 BlockPool 的字典层拼 4 字节区分。

## 2. 拍二：waiting 请求上车前查一次

只有 waiting（新请求或重放请求）会在分配前查缓存，入口是 `get_computed_blocks`（kv_cache_manager.py:183）：

```python
if not self.enable_caching or request.skip_reading_prefix_cache:
    return self.empty_kv_cache_blocks, 0

# 即使全部命中，最后一个 token 也要重算（要新 logits）
max_cache_hit_length = request.num_tokens - 1
computed_blocks, num_new_computed_tokens = \
    self.coordinator.find_longest_cache_hit(
        request.block_hashes, max_cache_hit_length)
```

三个要点：

1. **只缓存满块**，所以命中长度是块对齐的；源码注释特别指出：减 1 个 token 在块对齐下可能触发**整个末块重算**（不是只重算 1 个 token）；
2. 某些情况跳过查询：请求要 `prompt_logprobs`、pooling 模型全池化、或显式标了 skip；
3. running 请求**不查**——它已经在车上，复用发生在抢占重放回到 waiting 时。

命中的块经 `touch` 增加引用计数（[篇 3](/blog/vllm-调度3-要n个token怎么摆进物理块/)讲过），从空闲队列摘出，这一步就把它们和"待驱逐"区分开了。

## 3. 拍三：惰性 LRU，没有主动清理线程

缓存块什么时候被赶走？答案是"**不主动赶，只在需要新块时顺带处理**"：

- 请求结束/被抢占调 `free` 时，块按**逆序**（尾块先）归还；引用归零的块进空闲队列**尾部**，并保留哈希、成为驱逐候选；
- 分配新块时从空闲队列**头部 popleft**；拿到的如果还带哈希（是别人的缓存），才真正执行驱逐、清掉哈希；
- 引用计数 > 0 的块永远不会被分到，也就不会被误驱逐。

效果就是 LRU：刚释放的尾块（哈希链更长、复用价值相对低）排在前面先被复用，热点前缀待在队尾更安全。**没有后台驱逐循环**——没有新分配就没有驱逐。

## 4. 交叉点：新客与被踢请求走同一段查询

回到篇 4 的问题。重放请求重新成为 waiting 后，和新请求走**完全相同**的 `get_computed_blocks → touch` 路径：

- 它之前释放的块只要还没被别人 popleft 走（大概率在队尾、还活着），哈希一查就命中，`touch` 拿回，**只重算没命中的部分**；
- 若中途已被重分配给别人，哈希不在了，那一段才真正整段重算。

所以"V1 抢占只有重算"指的是机制上**没有 swap**；实际重算量由前缀缓存决定——块活着就便宜，被驱逐了才全量。

## 5. 边界与一个进阶机制

- **只利 TTFT、不利 ITL**：缓存省的是 prefill；running decode 每步本来就要算。
- **重启即失效**：缓存只在进程内存里，不持久化（跨实例持久化是 connector/LMCache 的事，见篇 8）。
- **多 KV group**：full attention + sliding window 混合模型，各 group 块大小要能整除；命中长度需要在各 group 间迭代收敛（只降不升），常见的简单混合走单轮短路。这是 `HybridKVCacheCoordinator` 的进阶话题，主线不依赖它。

## 自测（答案点击展开）

**1.** 为什么哈希要把"父块哈希"也编进去？只哈希本块 token 会出什么问题？

**2.** 一个 40 token 的 prompt、block_size=16，理论最多命中多少 token？为什么不是 39？

**3.** running 请求在普通 decode 步会查前缀缓存吗？被抢占重放时呢？

**4.** vLLM 有没有一个后台线程定期驱逐冷门缓存块？真实的驱逐在什么时候发生？

<Expand title="参考答案">

1. 防位置误命中：同一批 token 出现在不同位置时 KV 因 RoPE 而不同；编入父哈希后，只有"从开头起整条前缀都相同"哈希才相等。
2. 最多 32（两个满块）。命中按满块对齐，max_cache_hit 虽是 num_tokens−1=39，但分配要求块对齐，第 3 块没写满不缓存；减 1 在对齐下也可能让整个末块重算。
3. 普通 decode 不查（running 不经过 get_computed_blocks）；被抢占后回到 waiting、重新调度时会查，幸存块因此能 touch 复用、减少重算。
4. 没有主动驱逐线程。free 时引用归零的块带哈希进空闲队列尾部成为候选，分配新块从头部 popleft、拿到带哈希的块时才清哈希完成驱逐（惰性 LRU）。
