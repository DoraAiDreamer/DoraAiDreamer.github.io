## 1. 钩子：全绿的大盘，和转圈的用户

周一早九点，公司的 AI 客服告警群安静得反常。值班同学打开监控：CPU 40%、内存富裕、网卡没满、Pod 全是 Running——**大盘全绿**。但客服群里用户已经炸了：回复开始卡，有人等了 8 秒还看不到第一个字（故事数字，仅为示意）。

### 先听白话版的故障链

不用任何术语，这个故障是这样发生的。大模型干活分两个动作：**先把你的问题读一遍，这一步吃算力；再一个字一个字往外吐，这一步吃显存搬运**。周一早高峰大家的问题变长了，「读问题」把引擎占住，正在对话的人就感到字一顿一顿；同时大家问的内容也变了——周五大家问「退款」，周一全在问「发票」——引擎里那份大家合用的「共用前缀记忆」接不上，每个会话要占的显存块变多。显存不够，引擎就把一些对话的记忆扔掉重算，新来的人只好排队等第一个字。

现在给这条链挂上名字：读问题叫 **Prefill**，吐字叫 **Decode**；等第一个字的时间叫 **TTFT**，相邻两个字的间隔叫 **ITL**；长 prompt 切片的机制叫 Chunked Prefill；合用底稿叫 APC；扔记忆叫抢占（preempt），重算叫 recompute。

有经验的值班同学不会看到 TTFT 涨就断言「是 prefill 被挤占」。同一个信号至少有四种原因，他会按顺序拆：**排队时间分位 → prompt 长度分布 → APC 块命中率 → prefill 计算时间**，一步步排除。这篇文章的核心主张就藏在这里：**这个故障能不能查，不取决于命令熟不熟，取决于你能在这条链上走通几层。**

<Expand title="▸一个精确化：为什么不能简单说「命中率下降导致 KV 需求上涨」">

单个请求的 KV 大小只由它自己的会话长度决定，命中率下降不会让它变大。真正发生的是：共享前缀块减少 → **全集群占用的总块数上升、重复 prefill 的算力需求上升**。差一个字，排障方向就不同——该看的是聚合块数和 prefill 算力，而不是给某个会话量 KV。

</Expand>

### 第二钩：一笔你现在就能算的账

钱的事先不看单价，先算一个跟价格无关的单位——**卡年**（一张卡跑一整年的量）：

比如 64 张卡，有效利用率比目标低 30%，那就是 $64 \times 30\% = 19.2$ 卡年——**相当于白养了 19.2 张卡一整年**。第二阶段再乘你公司的单卡年成本（采购折旧或云租约，含机柜电），数字自己会说话。

注意围栏：这个 30% 是相对**目标利用率**的缺口，不是相对 100%。冗余（N+1、双 AZ、金丝雀容量）是必需品，利用率逼近上限时延迟会爆炸——怎么定目标利用率，是第 7 层的功课。

## 2. 先画边界：AI Ops 是什么，不是什么

**AI Ops（本文口径）＝让大模型、尤其是在线推理服务，在有限 GPU 预算内稳定、低成本地跑起来并持续变好的工程岗位。** 它和四个相邻岗位容易混：

| 对比 | 分界 |
| --- | --- |
| vs 传统 SRE/运维 | 底座相同，工作负载的物理规律不同——这正是全文主线 |
| vs 算法/模型工程师 | 人家产模型，你管模型在生产环境的命运；边界产物是「权重 + 推理配置」 |
| vs MLOps/平台工程师 | MLOps 偏训练流水线与实验管理，AI Ops 偏在线服务、GPU 资源与成本；小公司常是同一拨人 |
| vs 旧概念「AIOps」 | 那是**用 AI 做运维**（告警降噪、异常检测），本文是**运维 AI**。未来两者会交叉，但能力图谱完全不同 |

## 3. L0「地」：底座，以及三条被改写的假设

传统运维/SRE 的本事，经验估计约七成可以直接迁移，这一节先说结论：**值钱的不是重学，是识别哪些老假设失效了。**

**直接迁移的**：Linux 排障、TCP/HTTP/DNS、容器与镜像、Kubernetes 工作负载/Service/Ingress、CI/CD、metrics-logs-traces 三件套、SLO/变更管理/故障复盘、RBAC 与密钥。这些一样不少全部作数。

**三条被改写的假设**，每条都是真实事故的来源：

- **「实例是无状态的」**：KV Cache 在显存里，实例带着正在解码的会话。缩容、漂移、重启都有真实代价——被扔掉的会话要 recompute，用户感到卡顿（L3 弹性节展开）。
- **「资源利用率看 CPU/内存就够」**：GPU 的「利用率」有好几种口径，SM Active 高不等于算力用满；显存占用高也不等于显存被有效使用（L1 展开）。
- **「请求是短时完成的 RPC」**：一个推理请求是 TTFT 之后持续数秒的**流式生命**，长连接、逐 token 返回、中途取消都是常态。HPA、滚动升级、超时、重试的语义都要重新想。

## 4. L1「卡」：GPU 的脾气

这一节回答：为什么同样的卡，有人跑得快有人跑不满——物理拓扑和资源语义是这一层的功课。

### 最小硬件模型

不深挖芯片架构，给到运维决策所需的粒度就够：

- **卡内**：GPU 里有成千上万个计算单元（SM）和一块高带宽显存（HBM）。Decode 阶段速度由显存带宽决定——[《一次推理的旅程》](/blog/一次推理的旅程-prefill与decode)算过，70B 模型在 H100 上纯权重搬运的下限约 42ms，这里不重推。
- **卡间**：同一台机器里，卡与卡之间走 NVLink/NVSwitch（高速）还是 PCIe（慢一截）；张量并行最怕卡跨 NUMA、跨 PCIe 交换机。
- **机间**：多机任务靠 RDMA（InfiniBand 或 RoCE）通信，它是多机任务的命门；NCCL 超时、某张慢卡拖垮整批，是这一层最常见的大案。

### GPU 的「利用率」是一组指标，不是一个百分比

这是本节最容易写错的地方，分四层口径看：

- **时间占空比**：nvidia-smi 的 GPU-Util 和 DCGM 的 203 号指标，口径是「采样期内至少有一个 kernel 在执行的时间占比」。有 kernel 在跑就算忙，不代表计算单元被填满。
- **SM 层**：`SM_ACTIVE`（1002）看有没有 warp 驻留，`SM_OCCUPANCY`（1003）看驻留了多少。NVIDIA 官方明确：**等待内存的 warp 也算 active**——所以 SM Active 0.8 只是「necessary but not sufficient」，不等于 80% 算力。
- **功能管线**：`TENSOR_ACTIVE`（1004）看活有没有落在 Tensor Core 上，另有 FP16/FP32 管线指标。
- **数据搬运**：`DRAM_ACTIVE`（1005）和 PCIe/NVLink 字节数，看活有多重、瓶颈在不在搬运。

一条常用排查路径：**SM Active 高 + Tensor Active 低** → 没走 Tensor Core 或算子太小；**SM Active 高 + DRAM Active 高** → 显存带宽 bound；再查时钟/功耗限频原因；这些都解释不通，最后才上 Nsight。

<Expand title="▸DCGM 的三个工程坑">

- profiling 计数器需要管理员权限（驱动 418.43 起）；
- 硬件计数器靠多路复用轮询，采样频率过高会出现 zeroes；
- DCGM 与 Nsight Compute/Systems 不能同时占用计数器，切换前要 `dcgmi profile --pause`；MIG 下 NVLink/PCIe/显存控制器是共享资源，不能按实例单独 profiling。

</Expand>

### 把一张卡分给多个服务：MIG / MPS / 时间分片

| 方式 | 机制 | 硬约束与坑 |
| --- | --- | --- |
| **MIG** | 硬件硬隔离：SM 按 1/7 切、显存按 1/8 切（含带宽切片） | A100 上**任何跨卡 P2P 都不支持**；H100/H200 新驱动仅支持同一 GPU 内 MIG 实例间 P2P，跨卡 NVLink P2P 仍不可用；**NCCL 不支持 MIG** → 无法用它打包需要张量并行的大模型；A100 上切换 MIG 配置需要 GPU reset |
| **MPS** | 软件方式让多个进程共享 SM | Volta 起可设每客户显存上限和 active thread%，但那是**上限不是预留**，kernel 仍可能落在同一批 SM 上；客户未同步就异常退出，可能株连整个 MPS server 和所有客户；用量在 nvidia-smi 里记到 server 进程，无法直接按租户读数。MPS 可以叠加在 MIG 之上 |
| **时间分片** | 多服务轮换上卡 | 没有任何隔离，只有上下文切换；互扰全看运气 |

### Kubernetes 怎么分卡

- **Device Plugin** 只解决「整数资源分卡」：GPU 以整张为单位，不能超卖，框架层不支持共享。
- **Topology Manager** 只做节点内 NUMA/PCIe 对齐，**不感知 NVLink/NVSwitch**；多机任务的 all-or-nothing（gang，要么全调度上要么一个都不上）需要 Volcano、Kueue/coscheduling 这类调度器扩展。
- **DRA（Dynamic Resource Allocation）**：官方文档口径，v1.30 首次引入、**v1.35 起 Stable**。它用 ResourceClaims + device classes 支持设备的申请、共享与池化，正在补 device plugin「整数资源、不能共享」的短板；新建集群可以优先按它的方式设计。

## 5. L2「引擎」：模型到底怎么吃显存

这是 AI Ops 与传统运维最大的能力断层，也是全文核心层。本节做「地图索引」：机制细节全部回链站内专文，本文只给机制文里没有的两样东西——**指标信号与决策时机**。每个提及都一句自包含，不读原文不影响理解。

### 5.1 显存三笔账

GPU 显存被三样东西吃掉：

- **权重**：70B 模型 FP16 权重约 140GB；
- **KV Cache**：每个 token 的 KV ＝ $2 \times \text{层数} \times \text{KV头数} \times \text{head\_dim} \times \text{精度字节}$；
- **运行时开销**：激活值、显存碎片、算子工作区。

由此得到一条最重要的运维推论：**能装下权重不等于能服务。** 权重是进门门票，真正决定并发上限的，是权重之外还剩多少显存给 KV。

光看公式没感觉，给一个可以模仿的手算例子。LLaMA-2 70B 的形状是 80 层、8 个 KV 头、head_dim 128、FP16（每数 2 字节）：

一个 8K（8192 token）prompt 的 KV 大约是 $320 \text{ KiB} \times 8192 \approx 2.5 \text{ GiB}$。这就是为什么「70B 装进 8 卡机」和「70B 能服务几十个并发」之间还隔着一整层功课——每个在场会话都在持续吃这笔 KV。数字的形状假设写在这里，换模型要重算。

### 5.2 一次推理的两阶段

Prefill 典型是算力 bound，Decode 典型是显存带宽 bound。两阶段的指标、痛点、扩容逻辑完全不同，机制细节见[《一次推理的旅程》](/blog/一次推理的旅程-prefill与decode)。记住这个区分，后面每个机制都要问一句「它治的是哪一阶段」。

### 5.3 引擎在调度什么

以下机制均按 **vLLM V1（0.21，当前默认）** 的口径描述；V0 在 0.21 已完全移除，只作历史。

- **连续批处理 → 治吞吐**：Decode 步之间插空，请求随到随上、随完随下，不必等一批全部跑完。机制细节见[《连续批处理》](/blog/连续批处理-每个迭代步重新组批)。**指标信号**：在跑请求数与有效 token 产出的比值；持续低位说明批没凑起来。
- **PagedAttention → 治有效显存**：KV 按 16 token 一块分页管理，消灭显存碎片。机制细节见[《PagedAttention》](/blog/pagedattention-给kv-cache装上虚拟内存)（那篇里 2–4× 的数字挂着 2023 年、A100、OPT 模型的条件，本文不重复）。**指标信号**：`vllm:kv_cache_usage_perc`——注意这是 V1 的名字，V0 旧名 `gpu_cache_usage_perc` 已移除，但不少第三方文档至今还在写旧名，配监控时别照抄。
- **APC 前缀复用 → 治 TTFT**：以满块（block size 16）为单位复用 KV，尾部未满块不缓存；能复用的长度最多到 `num_tokens − 1`，最后一个 token 必须重算以取 logits（最坏情况整个末块重算）。官方 Limits 的原话是：APC 只减少 prefill 阶段的时间、不减少 decode 阶段的时间，且「in general does not reduce performance」。翻译成口径：**对单个请求，它只改善 TTFT、不改善 ITL；对前缀复用型负载，它同时提高吞吐与 goodput，并降低被抢占后 recompute 的代价。** V1 默认开启，哈希默认用 sha256，多租户有 cache_salt 做隔离。**指标信号**：`vllm:prefix_cache_hits` / `vllm:prefix_cache_queries` 是**块级** counter（不是请求命中率，算命中率用二者相除）；另有 `vllm:prompt_tokens_cached`。命中率是热点迁移的体温计——掉点往往先于 KV 上涨和抢占，是故障链上最早的可观测信号。
- **Chunked Prefill → 治 Decode 卡顿**：长 prompt 切片后插入迭代，避免一次占住引擎让在场会话全卡住。默认开启，**默认预算按硬件和使用场景分档**：API 服务场景，H100/H200/MI300x 级（显存 ≥70GiB 且设备名不含 A100）每步 8192 token / 最多 1024 条序列；A100 及更小卡为 2048 / 256；离线批处理场景的档位更大（16384 / 8192）。源码里那个 2048 常量只是测试兜底，不是线上默认值；A100 被特意排除在大预算外，因为大预算在 A100 上反而降吞吐（PR #17885）。
- **抢占 → 故障信号，不是优化项**：显存不够时 V1 只有 recompute 一条路（无 swap、无 COW）；被抢占的请求 KV 全部释放、计算进度归零，回到等待队列最前面，且发生抢占的那一步不接纳新请求。**指标信号**：`vllm:num_preemptions` 是累计 counter，要用 `rate()` 看增量；它的任何持续毛刺都意味着容量或流量出了问题，需要和排队毛刺配对看。

### 5.4 部署形态的四个杠杆

每个杠杆都是能力图谱上的一格，机制各有专文：

- **并行**：张量并行要求卡间高速互联（NVLink），流水线并行可以跨机；怎么拆先看硬件拓扑，不是参数越大越好。
- **量化**：FP8 需要 Hopper/Ada/Blackwell 代际，**A100 不支持 FP8**；AWQ、GPTQ 适用面更广。省显存的代价是校准和精度验证，见[《大模型量化》](/blog/大模型量化-用更少的显存跑更大的模型)。
- **投机解码**：小模型打草稿、大模型一次批改，1.5–3× 是有条件的区间、收益非单调，见[《投机解码》](/blog/投机解码-小模型打草稿大模型一次批改)。
- **PD 分离**：把 Prefill 和 Decode 拆到两个专用卡池。当前仍是 experimental，官方文档有一句加粗原话：**「DOES NOT improve throughput」**——它改善的是 SLO 内的 goodput、压制尾部 ITL，代价是多一整套 KV 迁移和双池运维，见[《PD 分离》](/blog/pd分离-把prefill和decode拆开部署)。

### 5.5 引擎之外：选型与生态

引擎本身不做排名：vLLM、SGLang、TensorRT-LLM、厂商 NIM 类产品按同一组维度比——生态与社区、定制深度、延迟-吞吐曲线、团队的长期维护力。产品形态为 **2026-09 快照，以官方文档为准**。

到 2026 年，光选引擎已经不够，平台层每天都在和三个名字打交道：

- **NVIDIA Dynamo**：K8s 原生的推理编排框架，NIM 类产品会内嵌其能力；注意它在没有 RDMA 时回退 TCP，性能损失很大。
- **Gateway API Inference Extension（GWIE）**：用 InferencePool + 外部调度策略（EPP）做请求级路由，带 Critical/Standard/Sheddable 三级优先级，过载时先 shed 低优请求。
- **vLLM Production Stack**：vLLM 官方的生产级前置组件集，补引擎本身不做的网关、多实例调度那一层。

## 6. L3「平台」：从一个服务到一个平台

这一节的每个话题都按同一个三列模板走：**Web 的老直觉 → 会出什么事 → 推理服务的正确姿势**。

### 权重分发与冷启动

70B FP16 权重约 140GB，冷启动要分清两种延迟：

- **加载延迟**：权重从对象存储/模型仓库拉到本地，受拉取带宽限制；常见做法是本地 NVMe 热缓存、预热常用权重、按需分页加载。
- **就绪延迟**：权重进了显存、Pod 报告 Ready 也不算完——CUDA Graph 捕获、kernel autotune、KV 池初始化、GPU 时钟从怠速爬升到加速频率，都在首批请求上完成。AWS 的 EKS 指南因此要求显式发 **100 个顺序请求预热**，再开始量容量。

取舍很直接：要 SLO 就保留预热/保温副本，把扩容滞后算进容量模型；靠懒加载省钱，就得接受扩窗内的降级。还要防**冷启动雪崩**：流量突增时多个副本同时扩容、集中拉权重，可能先把存储和网卡打满。

### 模型网关

统一的 OpenAI 兼容入口之后，网关要做：按模型路由、多租户配额与限流、按 token 计量计费。流式响应下「超时」和「取消」语义特殊——客户端断开后，引擎侧请求要不要立刻 abort、abort 后 KV 块什么时候释放，都得有明确策略（NIXL、Mooncake 连接器默认在 **480 秒**后释放未被消费的 KV 块，防止块被无限占用）。

### 弹性伸缩：不能照搬 CPU-HPA，但也别只认队列

老直觉是「CPU 高了就加机器」；在推理服务上直接照搬会出两类错：缩容等于蒸发显存里的会话；而 GPU 利用率作为扩容信号方向反了——**高利用率恰恰可能是健康的**。

但「只看队列、不看 GPU 利用率」同样是口号。生产里用双信号：

- **请求面指标是主轴**：等待队列长度、running 槽位、KV 占用；
- **延迟是独立的第二信号**：存在「延迟先涨、队列还没堆起来」的负载模式，单看队列会扩容过晚；冷启动期队列恒为 0、引擎却还没就绪，也是盲区；
- **DCGM/GPU 指标负责归因和兜底**：账单与容量口径、装箱与混部、scale-to-0 判定，以及「队列在涨，到底是算力满还是 KV 满」都要靠它。

AWS EKS 指南给出的一组**起始**阈值（来自其 8B 模型实测，不是通用标准，要按自己的压测结果重定）：队列深度 > 25 持续 30–60 秒扩容；P95 端到端延迟 > 5 秒作为同窗口第二信号；缩容要求队列归零且 P95 端到端延迟 < 3 秒持续 5 分钟。

### 缩容：一套只能慢、不能快的序列

「drain 式缩容」一句话带过会埋雷。流式会话的寿命由 `max_tokens` 决定，单请求可能数分钟到数十分钟，「等所有在途请求自然结束」常常等不起。正确顺序：

- preStop 先从网关**摘流**，并等网关端点收敛（否则新请求还在进来）；
- **有界 drain**：设时间上限，让在途请求尽量走完；
- 超时则显式 abort，让客户端按幂等键重试，并配合退避防止重试风暴；
- PD 场景下先停止向该 Decode 实例做新的 handover，再评估在场会话能否迁移。

### 发布、高可用与混部

- **发布升级**：引擎版本升级可能改变调度语义——历史上 V0→V1（0.8 起 V1 默认）就是最典型的一次：chunked prefill、APC 变为默认，抢占从 swap/recompute 两条路收成仅 recompute。灰度要同时按流量和按模型做，金丝雀盯分位 TTFT/ITL 和缓存命中率；长连接下的滚动升级要给连接迁移或重试策略。
- **高可用**：掉卡（Xid/ECC 错误）靠识别 + 节点 drain，NCCL hang 需要看门狗强制打断；推理引擎没有「主从」概念，高可用在流量层和数据层做；跨 AZ 部署要算清额外成本。
- **训练推理混部**：互扰不只在 SM——训练会吃满 HBM 带宽、NVLink、PCIe、RDMA 乃至电源和时钟。生产可行形态是**物理分池 + Kueue/KAI 类配额与优先级回收**；而优先级回收的延迟是分钟级（取决于检查点），这本身就是 SLO 风险，不能乐观地当成无缝分时复用。

## 7. L4「账」：让每块钱都算数

这一层是中级到高级的分水岭：怎么知道服务好不好、卡够不够、钱花得值不值。

### 7.1 LLM 服务的指标体系

口径先钉死，同一条曲线口径不同能差出一个数量级：

- **延迟**：TTFT、ITL、TPOT、端到端延迟，必须分 P50/P90/P99。还要区分**服务端观测与客户端观测**：服务端 TTFT 从请求到达前端起算，**已经包含排队和输入处理**，不能拿它当纯 prefill 时间——归因要用 `vllm:request_queue_time_seconds` 和 `vllm:request_prefill_time_seconds` 拆开。
- **吞吐**：tokens/s 要区分 output token 和 total token；真正该考核的是 goodput。
- **水位**：`vllm:num_requests_running` / `num_requests_waiting`（gauge 是刮取时刻的快照，秒级尖峰会漏）、`num_requests_waiting_by_reason`（capacity/deferred）、`kv_cache_usage_perc`、块级命中率、`num_preemptions`。
- **排队时间单列**：利用率升高时，队列延迟呈非线性上涨——容量红线就来自这里，而不是来自某个利用率百分比。

两个统计陷阱值得单列：跨副本的 P99 **不能对各 Pod 的 P99 取平均**，要用 `histogram_quantile` 配合 `sum by (le)` 聚合；客户端超时后 abort 的请求在服务端直方图里缺失（幸存者偏差），所以 **SLO 达成率必须由客户端/网关口径统计，服务端口径用于归因**。

### 7.2 压测：找拐点，不是找最大值

固定 prompt、固定输出长度只能测出引擎上限，测不出生产风险。靠谱的压测要：

- **回放真实 trace**：输入/输出长度分布、请求到达节律、长 prompt 尖峰、多模型混合、取消率；真实流量远非均匀到达（BurstGPT 等 trace 的突发很强）。
- **开环施压**：k6 的 constant-arrival-rate 这类生成器按固定节律发请求、不等上一个返回；而 `vllm bench` 默认 `request-rate=inf` 是闭环口径（客户端自我节流），会高估容量，必须设有限到达率。
- **防 APC 作弊**：用随机词让前缀缓存基本不命中（AWS 示例的做法），否则测出来的是缓存的速度不是引擎的速度。
- 目标只有一个：**找到拐点——在哪个并发度 P99 TTFT 破 SLO**，而不是跑到引擎崩掉记一个最大 QPS。

### 7.3 容量规划：两个一阶工具，和它们的边界

- **Little’s Law**：$L \approx \lambda W$，在途请求数 ≈ 到达率 × 单请求生命周期。它是稳态守恒等式，**不要求泊松到达**；Decode 生命周期长，所以推理服务在很低到达率下也有大量请求在场——这解释直觉完全正确。但它**不是容量预测模型**：停留时间 W 本身随负载变化，不能拿低负载时测的 W 外推高负载；均值只给平均在途数，槽位规划必须用长度分布和到达尖峰，SLO 拐点仍由压测确定。它的正确定位是**车队级的量级 sanity check**。
- **42ms 带宽下限**：这是 H100 SXM（3.35TB/s）、dense 70B、BF16、batch=1、只算权重且假设带宽跑满这一组条件下的 Decode 单步下限。**同口径**（同硬件、同 dtype、batch=1、稠密模型、按 step）实测低于它，说明测量口径对不上（常见：把多 token 一步当单 token、客户端采样、dtype/并行口径不一致）。换 H200（4.8TB/s，约 29ms）、B200（约 8TB/s）、FP8 权重减半、MoE 每 token 不读全量权重，锚点都要重算，不能外推；H100 PCIe 带宽只有 2.0TB/s，对应下限约 70ms。还有一个例外：**投机解码一个 step 可以发出多个被接受的 token，按 token 计的 TPOT 可以低于这个下限**——下限管的是单步，不是单 token。

容量规划的产出链条是：**给定流量与 SLO → 需要的 KV 槽位 → 卡数**，而不是「看着利用率加卡」。

### 7.4 成本工程

核心是一个让所有方案可比的单位：**每百万 token 成本**，输入和输出分开（输出占 Decode 卡时，单价通常显著更高）：

「全资源成本」至少包含：卡折旧/租金 + 主机 CPU/内存/NVMe + IB 网卡和交换机分摊 + **电力 × PUE + 机房** + 商业软件许可与支持 + 运维人力摊销 + 权重存储和跨 AZ 流量。PD 分离还要计入两个池各自的碎片与空载（池越多空载越大）、连接器占用的 CPU/内存/网卡、双 AZ 成本。

成本杠杆每个都要标明它动的是哪笔账：量化、批处理密度、APC 命中、PD 配比、混部、竞价/包月组合——分别动 TTFT 还是 ITL、吞吐还是 SLO，代价条件是什么，不标清楚就只是「降本大法」的名词橱窗。

### 结论会随规模反转

同一条经验，在小规模和大规模可能方向完全相反，搬别人答案前先看规模：

- **PD 分离**：小规模要为此空出整卡池，几乎永远不划算；大规模车队才有账可算。
- **MIG**：单机打包多个小模型很香；车队级只跑单一大模型时几乎用不上。
- **GPU 利用率信号**：单实例小规模可以凑合当容量信号；多租户大规模必然失真。
- **TP 跨机**：小规模碰不到互联瓶颈；多机场景它就是命门。

## 8. 两条纵贯线

### 纵贯一：编码与自动化

- **Python 是底线**：读得懂引擎报错、写得出评测/压测/对账脚本，而不只是会用现成平台。
- **声明式地固化操作**：用 operator/controller 把 GPU 节点自愈、权重分发这类运维动作变成 K8s 的声明式接口。
- **读源码和 changelog 的能力比熟练度保值**：引擎机制版本间会变（V0/V1 就是先例），命令和默认值会过期；能从源码确认「当前版本到底怎么工作」，是高级工程师的标志。
- **自己先当 AI Ops 的第一批用户**：用 AI 编程工具和 agent 做告警总结、日志归因、变更草拟可以提效，但证据核对和最终决策必须人来兜底。

### 纵贯二：可靠与安全

- **故障模式库**：三类 OOM 要分清——权重加载 OOM（装不下）、前向激活/碎片 OOM、KV 块分配失败；注意 **V1 里 KV 分配失败走抢占路径，通常不表现为 CUDA OOM**，找报错时别认错。另有掉卡 Xid、NCCL 超时、KV 迁移失败、冷启动雪崩。
- **流式调用的可靠性**：限流、退避、熔断要按流式语义实现；客户端无脑重试会酿成重试风暴。
- **安全合规**：镜像和权重的来源供应链、多租户数据隔离、显存数据残留、prompt 注入与输出审计（偏应用安全，网关责任点到为止）、密钥不出宿主机。
- **最危险的变更**：驱动 / CUDA / 引擎 / NVSwitch 和 IB 固件的版本联动——升级前矩阵核对，升级后专项验证。

## 9. 级别锚点：初/中/高/资深差在哪

级别不由年限和名词量决定，由两件事决定：**能下探到第几层、权衡半径有多大**。责任半径的单位是：**一个实例（中级）→ 一组服务（高级）→ 整个组织（资深）**。

行为锚点矩阵每格都按「动词 + 对象 + 证据」写，不用「精通」「了解」这类无法判定的词。先看三个示范格：

- **L0 · 中级示范**：能用 `kubectl describe`、events 和内核日志独立还原一次 Pod 漂移时序，并产出复盘时间线。
- **L2 · 中级示范**：能用 `prefix_cache_hits / prefix_cache_queries` 算出块命中率，并说出掉点的三种原因。
- **L4 · 高级示范**：能用压测拐点和成本模型给出「拆/不拆 PD」的决策书，且写明反悔条件。

其余格子沿着这个模板对号入座。大公司和小公司的同级别日常不同——大厂资深可能只在两层极深，小厂高级可能五层全包——所以每级都允许两种行为变体，**看行为不看 title**。

<AIOpsRecFig6 />

*图 5：三道分水岭各有一个可证伪的动作；级别是合取轮廓，不是平均分。*

三道分水岭，每道都有可证伪的验收点：

- **会装 → 会算**：动手前把 KV、容量、成本算到**量级**，事后被实测验证。算不是考场推导，是让自己的预估和实际数字同量级。
- **会调 → 会权衡**：真正的权衡有三问——哪两个可量化目标在交换？拐点在哪里？**反悔条件**是什么（出现什么信号就推翻决策）？三问答不全，就是自信地拧旋钮。
- **会守 → 会建**：「建」的验收是——机制被 ≥2 个人或场景复用、替换掉一个人肉动作或一次复盘结论、并且写明这个机制自身的失败模式。

两句反鸡汤围栏也放这里：分水岭是**累积**的，不是一次跃迁，多数人长期停在「算」与「权衡」之间是正常形状；它不是工龄钟，也不是晋升承诺。

## 10. 怎么用这张图：自评与补图

### 0–4 证据量表

每一级都绑定证据，消灭「我知道这个概念」式的橡皮分：

| 分数 | 标准（要拿得出证据） |
| --- | --- |
| 0 | 没听过 |
| 1 | **听得懂**：能向同事复述，并指得出它在 metrics/日志里的对应位置 |
| 2 | **跟过**：在 runbook 或评审指导下完成过，产出经人验收 |
| 3 | **背过**：在 ≥2 种不同情境下独立处理、为结果签名；半夜告警你是被 @ 的人 |
| 4 | **建过**：你设计的机制被团队复用，并能据此评审别人 |

2 分和 3 分有一句口诀：**出事时第一个把现象解释清楚的人是不是你。**

用法：每层挑 2–3 格（全文共打 12–15 格），每格写下证据日志（哪次事故、哪次对账），画出自己的五层轮廓，重点找**断层格**——上层已经 3 分、下层还是 0–1 分的位置（典型：会调 vLLM 参数但讲不清 KV 账）。

### 定级是合取轮廓，不是平均分

打完分散的格子，按合取规则收敛：

- **中级轮廓**：L0/L1 全部 ≥2，且 L2 至少有 2 格 ≥3；
- **高级轮廓**：在中级基础上，L3/L4 各有至少 2 格 ≥3，且其中至少 1 格达到 4；
- 其余组合落在两级之间，不用硬凑。

三份典型答卷长这样：**典型中级**——底座扎实、引擎账算得清，独立背一个在线服务；**大厂高级**——在伸缩/容量两格建过被全公司复用的机制，硬件细节未必亲手碰；**小厂全栈高级**——五层都在 2–3 分、没有 4 分，但一个人能从掉卡扛到账单。三种都是高级。

### 补短课程表

L2 机制按顺序读，每篇配一个「达 3 分」的动作标准：

- [《图解大模型》](/blog/图解大模型-一口气搞懂大模型的骨架)——能默画出 Transformer 主干和数据形状；
- [《一次推理的旅程》](/blog/一次推理的旅程-prefill与decode)——能对别人讲清两阶段和 42ms 的条件；
- [《PagedAttention》](/blog/pagedattention-给kv-cache装上虚拟内存)——能说清块管理解决什么、2–4× 的时代条件；
- [《连续批处理》](/blog/连续批处理-每个迭代步重新组批)——能对照指标说明批是怎么动态组成的；
- [《大模型量化》](/blog/大模型量化-用更少的显存跑更大的模型)、[《投机解码》](/blog/投机解码-小模型打草稿大模型一次批改)、[《PD 分离》](/blog/pd分离-把prefill和decode拆开部署)——能分别说出它们动哪笔账、代价条件。

L1/L3/L4 以官方文档为主：DCGM 字段手册、Kubernetes（含 DRA）、vLLM 官方文档、Google SRE 书，并在实验环境把钩子故事亲手复现一遍。想动手看实战，去[推理加速专栏](/inference/)。

要避开的反模式：证书和收藏夹堆砌、把「听过机制名」当能力、只学一家引擎的操作姿势、跳过底座直接学调参。团队负责人可以把第 9 节矩阵用于定级对话，每季度开一次地图校准会、用量表找团队短板。

## 11. 收束：哪些格子会变，哪些不会

- **会变的**：引擎和产品的名字、默认值、云产品形态、工具链——约占图谱表层，每半年都可能翻新。
- **不会变的**：显存与带宽的物理账、排队与容量的数学、流式请求的生命周期、成本与 SLO 的权衡——这些学会一次，长期复利。

回到周一那个早上：**现在再看那 8 秒，你能走通几层了？** 当大盘全绿而用户转圈时，这张图是排查路线；当预算被砍时，它是杠杆清单。地图会过时，但读图的能力不会。

## 12. 自测（答案折叠）

<Expand title="▸自测 1：nvidia-smi 利用率高，为什么不代表服务跑得好？">

至少两种情况：① 利用率是「有 kernel 在跑」的时间占空比，小算子没把 SM 填满也算忙；② warp 在等显存数据时也算 active，带宽 bound 的算子 SM Active 可以很高但吞吐低。此外还要排除时钟/功耗限频。要判断真实情况得看 SM Active、Tensor Active、DRAM Active 这一组指标。

</Expand>

<Expand title="▸自测 2：70B 权重能装进 8 卡机，为什么仍可能服务不了几个并发？">

显存三笔账：权重只是门票（约 140GB），每个在场会话还要持续吃 KV（70B 形状约 320 KiB/token），另有运行时开销。能服务的并发数取决于「权重之外剩下多少显存给 KV」，而不是取决于权重装不装得下。

</Expand>

<Expand title="▸自测 3：缩容在 LLM 服务上比普通 Web 服务多什么代价？">

实例显存里带着正在 Decode 的会话 KV，直接杀掉会让这些会话 recompute、用户卡顿。所以要摘流 → 等端点收敛 → 有界 drain → 超时 abort 加幂等重试，整个过程只能慢不能快。

</Expand>

<Expand title="▸自测 4（加分）：P99 TTFT 涨了但 ITL 没涨，怎么排查？">

问题不在 Decode 层，但不能单因反射。按鉴别链顺序：先看 `request_queue_time_seconds` 分位（排队）→ 再看 prompt token 长度分布（输入变长）→ 再看块级 APC 命中率（复用下降）→ 最后看 `request_prefill_time_seconds`（纯 prefill 计算）。前三个都排除，才归因 prefill 算力。

</Expand>

<Expand title="▸自测 5（加分）：「上 PD 分离提升吞吐」错在哪？">

PD 分离当前仍是 experimental，官方文档原话是「DOES NOT improve throughput」——它不提升裸吞吐，改善的是 SLO 内 goodput 和尾部 ITL；同时新增 KV 迁移、双池碎片与空载等运维成本，小规模通常不划算。

</Expand>

<Expand title="▸自测 6：算每百万 output token 成本，需要哪几个数？">

分子：期间全资源成本——卡折旧/租金、主机资源、网络分摊、电力 × PUE 与机房、软件许可、人力、存储与跨 AZ 流量。分母：同期的 output goodput token 数（按满足 SLO 口径，不用裸 SM 占空比）。输入和输出 token 分开算，输出单价通常更高。

</Expand>
