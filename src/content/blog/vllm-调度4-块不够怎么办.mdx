准入闸门、LIFO 抢占、只重算不换出——专题题眼

源码版本：**vLLM 0.21.0**（2026-05）。本系列锁定该版本，源码链接指向 v0.21.0 tag。

[篇 2](/blog/vllm-调度2-一个step里让谁推进)留了一个悬念：`allocate_slots` 返回 None 怎么办。[篇 3](/blog/vllm-调度3-要N个token怎么摆进物理块)只讲了成功路径。这一篇兑现它——这是整个调度器里最容易在生产中出问题的部分，也是本专题的题眼。

同一个 None，出现在调度的两个阶段，处理方式完全不同：

## 1. 第一道防线：准入闸门

在分配失败之前，waiting 请求还要先过一道闸——`scheduler_reserve_full_isl`（默认 **True**，scheduler.py:140）。它通过 `full_sequence_must_fit=True` 传进 `allocate_slots`：

```
if full_sequence_must_fit:
    # 按"完整输入序列"估算需要多少块（计入前缀命中与滑动窗口）
    num_blocks_to_allocate = self.coordinator.get_num_blocks_to_allocate(
        ..., num_tokens=min(request.num_tokens, self.max_model_len),
        apply_admission_cap=True,
    )
    if num_blocks_to_allocate > self.block_pool.get_num_free_blocks():
        return None
```

三点要钉死：

- 它检查的是**完整输入序列长度（ISL）**，不是”第一块 chunk 装不装得下”。否则 chunked prefill 只检查当前块，会先放进来、走到一半才发现没位置；
- 它是**可行性估算，不是物理预留**——通过闸门不代表这些块被锁定，真正分配仍在后面；
- **被抢占后重新调度（resumed）的请求也走这道闸**：装不下就继续留在 waiting 队首。这是抢占之外防止饥饿的第二道。

## 2. 触发抢占：是 running 请求的下一块失败

注意触发点——不是”新请求抢座位”，而是**一个已经在车上的请求，为它下一步的 token 分块时分不出来**：

```
while True:
    new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens, ...)
    if new_blocks is not None:
        break                       # 分到了，继续

    # 分不到：抢占一个请求腾出块
    if self.policy == SchedulingPolicy.PRIORITY:
        preempted_req = max(self.running,
                            key=lambda r: (r.priority, r.arrival_time))
        self.running.remove(preempted_req)
        if preempted_req in scheduled_running_reqs:
            # 本步已经调度过的受害者：预算、块、编码器都要完整回滚
            ...
    else:
        preempted_req = self.running.pop()    # FCFS：踢最后上车的
    self._preempt_request(preempted_req, scheduled_timestamp)
    if preempted_req == request:
        break                                # 踢到自己了，这步放弃
```

为什么 FCFS 用 `running.pop()`（踢列表末尾，即最晚加入者）？**保护早到的请求**：它们已经投入了最多的 KV、往往也最接近完成；踢掉最新的，损失最小。PRIORITY 策略则选 `(priority, arrival_time)` 最低的。

一个容易忽略的细节：如果被选中的受害者**本步已经被调度过**（在 running 循环更早处拿到了预算和块），必须把它的 token 预算、分到的块、编码器预算、请求索引全部回滚，否则这一步的账就对不上。

## 3. 抢占动作：释放、归零、回队首

`_preempt_request` 把动作做全（scheduler.py:910）：

```
def _preempt_request(self, request, timestamp):
    self.kv_cache_manager.free(request)          # ① 释放 KV 块
    self.encoder_cache_manager.free(request)     # ② 释放编码器缓存
    request.status = RequestStatus.PREEMPTED
    request.num_computed_tokens = 0              # ③ 进度归零
    if request.spec_token_ids:
        request.spec_token_ids = []             #    清投机草稿
    request.num_preemptions += 1
    request.record_event(EngineCoreEventType.PREEMPTED, timestamp)
    self.waiting.prepend_request(request)       # ④ 回 waiting 队首
```

归四组记：**free KV / free encoder / 状态与游标归零（含清 spec、计数、事件）/ 回队首**。调用方（抢占循环）负责把它从 running 列表移除——这个方法只改这个请求自己。

回队首是为了让它**下一个 step 优先重放**（还要再过一次准入闸）。客户端并不会收到错误：请求仍在引擎内等待，没有超时上限，只靠外层网关兜底。

## 4. 只重算，不换出

**V1 的抢占只有 recompute 一条路**：KV 释放后，重新调度时把 prompt（加已生成文本）重新做一次 prefill。

对照历史：vLLM 论文（2023）时代有两条路——换出到 CPU 内存（swap）或重算；V0 两者都支持。V1 移除了 swap，原因是现代 KV 量化、前缀缓存普及，重算更简单，而且幸存的前缀块能让重算变便宜（见[篇 5](/blog/vllm-调度5-相同前缀为什么不用重算)）。

## 5. 为什么发生抢占的 step 不接纳新请求

回到[篇 2](/blog/vllm-调度2-一个step里让谁推进)的三阶段，waiting 循环的第一行条件是：

```
if not preempted_reqs and self._pause_state == PauseState.UNPAUSED:
    ...  # 只有这一步没人被踢，才开门接新客
```

如果一边踢人、一边还放新请求进来，被踢的请求可能反复被挤、永远轮不上（饥饿）。所以这一步的预算全部留给 running 和被踢请求的恢复。

## 6. 小结

引擎尽量不让请求走到”分不到块”：waiting 先过完整 ISL 准入闸、resumed 也得过；真到了 running 请求的下一块分不出来，才按 FCFS-LIFO（或 priority）踢一个、释放 KV/encoder、进度归零、回队首，下个 step 重放——只重算不换出，且这一步不再接新客。

被踢请求重放时能复用多少缓存，是篇 5；线上怎么从监控看到抢占，是篇 6。

## 自测（答案点击展开）

**1.** 准入闸门为什么按**完整**输入序列估算，而不是当前 chunk？它是物理预留吗？

**2.** FCFS 下为什么踢 `running.pop()`（最晚加入者），而不是随便挑一个？

**3.** 受害者如果本步已经被调度过，抢占时除了释放块还要做什么？为什么？

**4.** V1 抢占后请求的 KV 去哪了？为什么客户端不会立刻收到报错？

<Expand title="▸参考答案">

1. chunked prefill 下只检查当前块会让请求先进场、走到一半才发现装不下；按完整 ISL 估算可在进场前拦下。它只是可行性估算、不是物理预留，块不会因此被锁定。
2. 早到的请求已积累更多 KV、更接近完成，踢最晚加入者损失的已投入计算最小，也保护早到请求不被后来者反复挤掉。
3. 要把本步已发给它的 token 预算、编码器预算回滚，从已调度集合移除并恢复 req_index——否则这一步的总预算和块账对不上。
4. V1 只重算：KV 全部释放，重放时对 prompt+已生成重做 prefill（论文/V0 时代还有 swap 到 CPU，V1 已移除）。请求回到 waiting 队首等待，状态是 PREEMPTED 而非失败，引擎内无超时上限，所以客户端只感到变慢，报错要靠外层网关。
