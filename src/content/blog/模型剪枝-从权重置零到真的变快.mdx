先做一个三十秒的实验。构造一个大权重矩阵做矩阵乘法，记下耗时；然后把其中一半元素置零，再跑一次。直觉上「一半的乘法不用做了」，应该快一倍——实测耗时几乎不变。这个反直觉现象就是模型剪枝（pruning）的入口：**把权重变成零很容易，让模型真的变小、真的变快，是另一门工程。**

<PrHookCard />

*图 1：50% 权重置零前后，矩阵形状、字节数、matmul 耗时都不变。数值仅为示意，实测随硬件与矩阵尺寸变化。*

更反直觉的是精度侧。SparseGPT（arXiv:2301.00774，ICML 2023）把 OPT-175B 一半的**线性层**权重一次性剪掉，不需要重新训练，单张 A100-80GB 约 4 小时完成；在 raw-WikiText2 上困惑度（perplexity，越低越好）从 8.34 变成 **8.21——不升反降**（论文 Table 1 原文）。作为对照，朴素地按绝对值剪掉最小的一半，困惑度直接崩坏到 $4.3\times10^4$。

精度像白送，速度却兑换不成。为什么？因为剪枝有三种彼此独立的「货币」：**存储体积、算术量、墙钟时间**。稀疏率只是算法指标——它只告诉你零的比例；零能不能兑换成更小的文件、更少的乘法、更短的延迟，各有各的兑换关卡。本文主线就是这三张兑换表，以及每条兑换路线上的代表方法与工具。

前置阅读：2:4 稀疏的硬件机制（Sparse Tensor Core 为什么恰好快一倍）在[《算力是什么》](/blog/算力是什么-从一张h100到万卡集群/)第 1 节讲过，本文不重复硬件流水细节，只补「模型侧如何变成合规稀疏」；量化（W8A8/W4A16、GPTQ/AWQ）见[《大模型量化》](/blog/大模型量化-用更少的显存跑更大的模型/)。

<Expand title="术语速查（先扫一眼，读完再回看）">

- **dense / sparse**：稠密（每个权重都有值）/ 稀疏（部分权重为零）。
- **mask（掩码）**：与权重同形的 0/1 矩阵，标记谁被剪掉；很多剪枝工具只挂 mask，不改形状。
- **结构化程度**：零的位置有多规律——完全随机叫非结构化，按固定小模式排列叫 N:M，整块整行为零叫结构化。
- **CSR/COO**：只存非零值加位置索引的压缩存储格式；不换格式，文件里的 0 照样占字节。
- **one-shot 剪枝**：训练后一次性剪掉，不重新训练（SparseGPT/Wanda）；IMP 是「训练—剪—重训」迭代。
- **kernel**：GPU 上实际执行矩阵乘等运算的底层程序；能不能跳零取决于它，不取决于权重里有没有零。

</Expand>

## 1. 先分粒度：零长在哪里，决定命运

剪枝方法可以按三个轴分类：**粒度**（零以什么模式分布）、**时机**（训练前、训练中还是训练后剪）、**判据**（按什么标准决定剪谁）。本节只展开最重要的粒度轴；时机与判据随历史在第 3、4 节展开，第 8 节再合体总结。

<PrTaxonomyFigure />

*图 2：同一个权重矩阵上的六种剪枝粒度（蓝块为保留权重，虚线空格为零）。前三类矩阵形状不变，后三类物理缩形。*

- **非结构化（unstructured）**：逐个权重独立置零，零可以出现在任意位置。压缩率上限最高，但形状不规则，GPU 很难利用。
- **N:M 半结构化（semi-structured / fine-grained structured）**：沿输入通道方向，每连续 M 个权重中恰好 N 个非零。2:4 是唯一有硬件加速的比例，Sparse Tensor Core 标称吞吐翻倍；其他比例（1:4、2:8、4:8 等）有研究但无对应硬件。
- **块稀疏（block sparsity）**：以小块（如 32×32）为单位整团置零，规则度介于两者之间，需要专门的 tile kernel。
- **结构化：通道/filter**：剪掉整个卷积核或整个通道——矩阵直接少一列（或少一行）。
- **结构化：注意力头（head）**：成组剪掉注意力的 Q/K/V/O 投影列。
- **结构化：层/隐藏维**：删掉整个 Transformer 层，或沿隐藏维度削窄（如 SliceGPT）。

这六类有个决定命运的分野：**前三类剪完矩阵形状不变**（零还在 dense 矩阵里，能不能跳零取决于 kernel）；**后三类物理缩形**（权重矩阵真的变小，任何 dense BLAS 都直接少算）。注意区分稀疏率的分母：「全局 50%」与「线性层 50%」、「2:4 固定 50%」并不等价——embedding 与 lm_head 通常不剪。

另外先划一条容易混淆的边界：**MoE 不是权重稀疏**。MoE 每个 token 只路由到少数专家，省的是激活计算（激活稀疏），但全部专家的权重照常存储、照常加载；稀疏注意力省的也是激活。本文讲的都是**权重稀疏**。

## 2. 变快的三个必要条件

把零兑换成墙钟时间，要连续通过三道关卡，任何一道没过，稀疏率就只是数字。

**条件一：物理上不读零（存储货币）。** 在 dense 张量里，`0.0` 和 `0.12` 占同样的字节，都要从显存搬到寄存器。文件变小必须换成压缩表示：CSR/COO 这类通用格式、位掩码，或 2:4 专用的「非零值+位置索引」。Deep Compression（Han 等，arXiv:1510.00149）报告的 35–49 倍压缩是**存储**口径，且是「剪枝+量化+哈夫曼编码」三件事的合力，不是延迟数字。

**条件二：有真正跳零的 kernel。** 仅把权重乘上 mask，dense GEMM 仍会把零搬进寄存器、照样发射乘加指令。要省算术量必须换成专用 kernel：cuSPARSE（通用稀疏）、cuSPARSELt（2:4 专用）、CUTLASS sparse GEMM、vLLM 的 Sparse-Marlin，或者干脆走结构化缩形。Tensor Core 只接收按固定 tile 摆好的整块数据，不会自动跳过散落的零。

**条件三：规则度足以摊平开销。** 通用稀疏 kernel 有索引查找、分支、合并访存的额外成本，而它的对手 cuBLAS dense GEMM 已经被优化到接近峰值。矩阵不够大、零不够密时，这些成本直接吃掉跳零收益——小矩阵上稀疏比 dense 更慢并不奇怪。

<PrSpeedupFigure />

*图 3：左账（理论乘法量）随稀疏率线性下降，人人会算；右账（实测墙钟）只有规则稀疏与物理缩形兑现，且都打折扣。示意曲线，非实测。*

三条兑换路径因此泾渭分明：① 非结构化 + 专用稀疏 kernel（CPU 生态较友好，GPU 上通常要 60–70% 以上稀疏才有净收益）；② 2:4 + Sparse Tensor Core（整齐的 50% 才值钱）；③ 结构化剪枝物理缩形（dense 后端直接受益）。

实际折扣有多大？Wanda 论文（arXiv:2306.11695，ICLR 2024，A6000 + CUTLASS 2:4 kernel）给出两个不同实验的数字，注意它们不是同一模型剖面：**LLaMA-65B、batch=1 的各线性层 kernel 微基准约 1.54–1.63 倍**；而 **LLaMA-7B 端到端生成延迟只从 312ms 降到 251ms（约 1.24 倍）**——softmax、归一化、采样等非 GEMM 段不被稀疏加速，decode 又被权重带宽卡住。Amdahl 定律对这种「只优化一部分」的折扣有理论解释，见[《算力是什么》第 4 节扩展阅读](/blog/算力是什么-从一张h100到万卡集群/)。

**演示 1：mask 置零为什么不加速（研究复现）**

- 依赖：`pip install torch`（2.x）
- 硬件：任意 CPU 即可，约 2 分钟
- 预期输出：mask 与权重形状相同；`nelement()*2` 字节数剪枝前后不变；两次 matmul 耗时基本相同

```python
import torch, torch.nn as nn
import torch.nn.utils.prune as prune

fc = nn.Linear(1024, 1024)
x = torch.randn(2048, 1024)

@torch.no_grad()
def bench():
    for _ in range(3): fc(x)          # 预热
    import time; t=time.perf_counter()
    for _ in range(20): fc(x)
    return (time.perf_counter()-t)/20*1000  # ms

print("dense:", round(bench(),2), "ms")

# 50% 非结构化剪枝：只挂一个 mask，forward 时 weight = weight_orig * mask
prune.l1_unstructured(fc, name="weight", amount=0.5)
print(fc.weight_mask.shape)                 # torch.Size([1024, 1024])——形状没变
print(fc.weight.nelement()*2, "bytes")      # 剪枝前后字节数完全一样
print("sparse:", round(bench(),2), "ms")    # 耗时基本不变：计算仍走 dense GEMM
```

同一个 API 还提供按范数剪行（`prune.ln_structured`）、跨层全局排序（`prune.global_unstructured`）、外部掩码（`prune.custom_from_mask`），以及 `prune.remove()`（把 mask 物化成零权重、恢复普通 Parameter）。它们解决的都是「怎么决定和表达掩码」，不解决加速——加速仍然要等专用后端或物理缩形。

<Expand title="扩展阅读：PyTorch 的 2:4 压缩表示（需 NVIDIA GPU）">

`Tensor.to_sparse_semi_structured()`（PyTorch 2.1 引入，**仍是 prototype**）能把 dense 权重转成 2:4 压缩布局，后端走 cuSPARSELt：

```python
# 仅 CUDA；FP16/BF16/TF32/INT8 需 Ampere 及以上，FP8 需 sm_89/90（Ada/Hopper）
w24 = torch.randn(1024, 1024, device="cuda", dtype=torch.float16).to_sparse_semi_structured()

```

无 N 卡的读者跳过即可；该路径算子覆盖少、形状约束多，随 torch 版本变化，生产中通常经 TensorRT/ModelOpt 使用（见第 6 节）。

## 3. 六种粒度逐个看

### 第一幕：不缩形三兄弟——命运在 kernel 手里

**非结构化。** 现代剪枝的起点是 Han Song 2015 年的三步法（arXiv:1506.02626）：正常训练 → 按幅度剪掉小权重 → 用剩余权重重新训练，迭代进行；AlexNet 参数减 9 倍、VGG 减 13 倍不掉点。彩票假设（Lottery Ticket Hypothesis，arXiv:1803.03635，ICLR 2019 最佳论文）进一步发现：密集网络里存在一个「中奖」子网络，用它的原始初始化单独训练就能匹敌原网，流程叫 IMP（迭代幅度剪枝+权重重置）。但这套范式在大模型上失效：Wanda 附录 C 显示，SNIP、Movement 等为 BERT 设计的判据直接用于 LLaMA-7B，困惑度崩到 89–349，微调后仍大于 72；百亿模型做多轮 IMP+重训的成本也不可行。post-hoc 可剪 ≠ 中奖票存在。

**N:M 半结构化（2:4）。** 规格表上的 structured sparsity 特指 2:4 细粒度模式（NVIDIA 白皮书 arXiv:2104.08378）；Zhou 等（arXiv:2102.04010，ICLR 2021）用 SR-STE 近似梯度首次从头训出满足 N:M 的网络，当代后继 S-STE（arXiv:2409.09099，NeurIPS 2024）支持全程 FP8 的 2:4 从头训练。但截至目前，没有公开的、经同行核验的「原生 2:4 训练旗舰 LLM」案例。模型侧变成合规 2:4 有三条路：训练时用 ASP/ModelOpt 约束（第 6 节）、从头稀疏训练（研究）、或训练后用 SparseGPT/Wanda 直接生成 2:4 掩码再微调恢复。

**块稀疏。** 以 32×32 之类的小块为单位剪，kernel 可以整 tile 跳过，规则度比随机稀疏友好。它也是稀疏注意力与 MoE 常用的计算组织方式——但再强调一次：那两类省的是激活计算，与权重剪枝是两件事。

### 第二幕：缩形的传统件——CNN 的主场

**通道与 filter 剪枝。** 直接删除整个卷积核（filter）或整个通道，权重矩阵的行列物理变短，普通 GEMM 立刻少算。代表工作：Li Hao 的 filter L1 范数剪枝（arXiv:1608.08710，ICLR 2017，VGG-16 推理成本 −34%、ResNet-110 −38%，CIFAR-10）；Network Slimming（arXiv:1708.06519，ICCV 2017）对 BatchNorm 的缩放系数 γ 加 L1 惩罚，γ≈0 的通道即可安全删除。今天检测、分割、端侧模型（YOLO 系列等）仍把结构化剪枝+蒸馏当常规手段，工程工具可看 Torch-Pruning（DepGraph 自动处理层间耦合）。

**「划名字」与「拆座椅」**：mask 置零像在名单上划掉乐手名字——人还坐在台上，整场演出时长不变；物理缩形则是撤销整个声部、重印曲谱、拆走座椅，任何指挥（后端）都能演得更短。中间还隔着节目单重排（kernel）。

**演示 2：物理缩形真的变快（研究复现）**

- 依赖：`pip install torch`（2.x）
- 硬件：任意 CPU，约 3 分钟
- 预期输出：切窄后的层耗时约为原层的 1/2（近线性下降），与演示 1 形成对照

```python
import torch, torch.nn as nn, time

big = nn.Linear(4096, 4096)
thin = nn.Linear(2048, 4096)          # 输入维物理切窄：矩阵少一半列
x1 = torch.randn(256, 4096)
x2 = torch.randn(256, 2048)

@torch.no_grad()
def bench(m, x):
    for _ in range(3): m(x)
    t = time.perf_counter()
    for _ in range(20): m(x)
    return (time.perf_counter()-t)/20*1000

print("4096->4096:", round(bench(big, x1), 2), "ms")
print("2048->4096:", round(bench(thin, x2), 2), "ms")   # 耗时近线性下降
```

真实网络里还要同步切掉下一层对应的输入行并做恢复微调——这正是结构化剪枝工具的工作。

### 第三幕：缩形的 LLM 件——注意力头的兴衰史

**注意力头。** BERT 时代的研究很乐观：Michel 等（arXiv:1905.10650，NeurIPS 2019）发现很多层只留一个头，单删任意一个头的指标变化都不显著；Voita 等（arXiv:1905.09418，ACL 2019）在机器翻译上把 48 个头剪到 10 个只掉 0.15 BLEU。但注意他们也测到：只做 mask、不物理缩形时，延迟根本不降。LLM 时代这事更难做了，两条原因并列：① 现代 LLM 里普适静态冗余的头很少——Sandoval-Segura 等（arXiv:2504.03889，ICLR 2026）发现平均超过 12% 的头是失活的，但失活是**上下文相关**的，只在特定输入上可消融（MMLU 保持 1% 以内），不是固定能删 12%；② GQA 共享的是 K/V 头（Q 头仍有 32 个之多），mask 掉 Q 头不改变任何矩阵形状，而 K/V 头本就只剩个位数，物理移除工程收益极小。

**层与隐藏维。** ShortGPT（arXiv:2403.03853）提出 Block Influence 指标（BI=1−层输入与输出的余弦相似度）来识别冗余层：LLaMA-2-7B 删掉 27.1% 的层（32→23 层），14 项基准的零样本均分保持稠密模型的 86.3%（无后训练）。加速数字要看清前提——论文 Table 4 的 1.08 倍/1.19 倍 token/s 是在 **GPTQ 4-bit 量化模型**上、删 12.5%/27.1% 层测得；删层直接减少每层权重搬运，decode 端受带宽限制所以折扣明显，这恰好又印证第 2 节的 1.24 倍现象。

SliceGPT（arXiv:2401.15024，ICLR 2024）更精巧：残差流是所有层共用的一条「公共走廊」，单层切一列，上下游就接不上了；它用校准数据算出一组正交旋转，把各层「不重要的方向」拧到同一组坐标轴上（正交变换保范数），对齐后整条隐藏维就能在所有层同时切除，权重直接变成更小的稠密矩阵。围栏也要立住：保范数不等于无损——Table 7 无恢复微调时，25% 切片让 LLaMA-2-70B 零样本均分从 76.57 降到 69.75（约 91%；论文按任务比率口径报告 96%，恢复微调后 99%）；部署侧 70B 从需要 4 张 A100-40G 降到 3 张（500→330 GPU-ms）。

## 4. 判据演进：按什么标准决定剪谁

判据的历史走了三步。**第一步只看权重本身**：幅度剪枝，绝对值小的先死，一行代码就能实现（演示 1）。**第二步看权重对层输出的影响**：OBD（LeCun 1989）/OBS（Hassibi 1993）用 Hessian 曲率衡量参数「显著性」；SparseGPT 是这条血脉在 LLM 上的后裔——它逐层求解一个局部 Hessian 重构问题，剪完立刻用剩余权重补偿误差，这是它 175B 免重训仍不掉点的关键。**第三步连权重更新都不要**：Wanda（Sun 等，ICLR 2024）的判据是 $|w_{ij}|\cdot\|x_j\|_2$——权重幅值乘以对应输入激活的范数，逐输出通道排序，不需要任何梯度更新。论文称该判据的计算比 SparseGPT 快 **300 倍**（Table 4 实测：7B 上 0.54s vs 203.1s 约 376 倍，65B 上 5.6s vs 1353.4s 约 242 倍；仅限指标计算，不是端到端剪枝），而剪枝质量基本匹敌。

<Expand title="折叠：判据的史前史">

- **BN gamma**：Network Slimming 利用 BatchNorm 缩放系数识别无用通道，是结构化剪枝最优雅的自动判据。
- **Movement Pruning**（Sanh 等，arXiv:2005.07683，NeurIPS 2020）：微调中「持续远离零」的权重留下，而不是看最终绝对值；配合蒸馏能把 BERT 剪到只剩 3% 参数。它是为迁移学习设计的，直接搬到 LLaMA 上会失效（见第 3 节 Wanda 附录 C）。

</Expand>

为什么需要校准数据？因为激活感知类判据要统计输入分布：SparseGPT/Wanda 都只需 128 条 C4 序列（每条 2048 token）跑一遍前向。embedding 层与 lm_head 通常跳过——它们对输入/输出分布变化最敏感，占参数比例又小，剪掉性价比低；非嵌入参数的绝大多数集中在线性层。

**演示 3：在小模型上复现 one-shot 剪枝（研究复现，非生产）**

- 环境：NVIDIA GPU + 独立旧 conda 环境。官方仓库 `INSTALL.md` 钉了 Python 3.9 / torch 1.10.1+cu113 / transformers 4.28.0 / datasets 2.11；`main.py` 硬编码 CUDA 与 fp16，C4 用旧式配置名加载，2026 年的新环境直接跑大概率报错
- 硬件耗时：OPT-125M 约 FP16 250MB 显存，分钟级；CPU 不是官方支持路径（需自行改 device、dtype 与数据加载三处，属读者改造项）
- 预期输出（OPT-125M，raw-WikiText2 困惑度，SparseGPT 论文 Table 1 原文）：

```text
dense（不剪）            27.66
magnitude（幅度剪 50%）   193      ← 朴素判据直接崩
SparseGPT（剪 50%）       36.89    ← 好判据救回大半
```

```bash
# SparseGPT：https://github.com/IST-DASLab/sparsegpt
python opt.py facebook/opt-125m c4 --sparsity .5          # 非结构化 50%
python opt.py facebook/opt-125m c4 --prunen 2 --prunem 4  # 全 2:4

# Wanda：https://github.com/locuslab/wanda（sparsity_type: unstructured / 2:4 / 4:8）
python main.py --model facebook/opt-125m --prune_method wanda \
  --sparsity_ratio 0.5 --sparsity_type unstructured
```

一张表讲两个教训：**小模型不耐剪**（125M 剪完仍明显变差，65B 剪 50% 却几乎追平 dense——「越大越耐剪」，但注意这是质量口径：dense 存储下剪完的 65B 成本还是 65B，且耐剪的是「大模型+好判据」的组合，配错判据照样崩）；输出 checkpoint 是 HF 格式的 dense-with-zeros——文件不缩小、默认推理不加速。正式跟做前请在干净环境锁定 requirements；跑不通时把它当「环境快照+预期数字」的导览即可。

## 5. 大模型剪枝路线图，与工业皇冠

| 路线 | 代表方法 | 是否重训 | 精度锚（带模型/条件） | 部署形态 |
| --- | --- | --- | --- | --- |
| 非结构化 one-shot | SparseGPT / Wanda | 免重训，可 LoRA 恢复 | LLaMA-7B 50% 零样本 −5.8pp；65B 基本追平 dense；80% 普遍崩溃 | 研究为主；2:4 有窄生产路径 |
| 结构化通道/维度 | LLM-Pruner / SliceGPT | LoRA 或短微调 | 7B 删 20% 参数保持 93.6%（v1；NeurIPS camera-ready 为 94.97%）；SliceGPT 70B 切 25% 见正文三口径 | dense 小矩阵，通用后端 |
| 层剪枝 + 蒸馏 | ShortGPT / Llama-3.2 / Minitron | 需蒸馏恢复 | 工业成品见下 | dense 少层，全部后端 |

**工业皇冠：剪枝在 LLM 时代的真正主场是「造小模型」。** 最有说服力的证据来自 Meta 官方：Llama-3.2 的 1B/3B 模型就是从 Llama-3.1-8B 做结构化剪枝、再用 8B/70B 的 logits 蒸馏得到的。更极致的 Llama Guard 3-1B-INT4（arXiv:2411.17713）把 1B 模型从 16 个 block 减到 12 个、MLP 隐藏维 8192 削到 6400（还剪了 unembedding 层），剪枝+蒸馏后再做 INT4 QAT，最终 11.2 亿参数、440MB（约为 FP16 版的 1/7），安卓中端 CPU 上超过 30 token/s。NVIDIA 的 Minitron（arXiv:2407.14679）从 Nemotron-4 15B 同时剪出 8B/4B 家族，4B 模型的 MMLU 比同等规模从零训练最高高 16 个点、最多省 40 倍训练 token。

**那在线推理为什么默认选量化而不是剪枝？** 量化（W8A8/W4A16）直接把每个权重从 16 比特压到 8/4 比特，砍的正是 decode 端最缺的权重带宽，kernel 生态成熟、精度损失通常一两个点（机制见[《大模型量化》](/blog/大模型量化-用更少的显存跑更大的模型/)）。剪枝与量化可以叠加：SparseGPT 报告 175B 上 2:4+4bit 的困惑度约 8.55，与纯 4bit 的约 8.3 只差 0.2–0.3（同表口径）；Neural Magic 的 A100 博客展示过 sparse+4bit 约 2.1 倍（博客口径，附特定 batch/序列条件）。收益场景要分清：**kernel 级近 2 倍最容易在算力受限的 prefill 大 GEMM 上兑现；端到端显著收益主要出现在权重带宽受限、线性层占比高的小 batch decode**，prefill 与大 batch 还要扣除非 GEMM 段——一律端到端 profiling 为准。

<Expand title="折叠：FP8 稀疏的口径差——datasheet 的 2 倍为什么实测只有 1.42 倍">

分三层看：**指令层**，Hopper 的 `wgmma.sp` 已支持 FP8 的 2:4（微基准论文 arXiv:2402.13499 的 Table I 如此列出），但同一论文实测 H800 上稀疏 mma 指令跨精度、跨 shape 的平均加速只有 **1.42 倍**；**库层**，cuSPARSELt 在 sm_89/90 已含 FP8（E4M3/E5M2）类型；**框架/引擎层**，Transformer Engine、TensorRT-LLM 等生产栈并未把「FP8×稀疏」这条组合接线——断档在引擎集成，不是硬件里没有 FP8 稀疏。Blackwell 的增量是 `tcgen05.mma.sp` 补齐 FP4（paired 4:8 模式）并逐步打通软件栈。发布时以 cuSPARSELt Support Matrix 与 PTX ISA 为准。

</Expand>

## 6. NVIDIA 工具链：唯一成体系的生产路径

本节代码需要 NVIDIA GPU（Ampere 及以上）+ Linux；没有 N 卡的读者把它当链路导览。

<PrToolchainFigure />

*图 5：NVIDIA 与昇腾的 2:4 生产链路同构：剪 → 调 → 导 → 逐层验证。最容易被忽略的是第四步。*

链路有四段：

1. **剪**。老牌工具是 **ASP**（Apex Sparsity，`apex.contrib.sparsity`），对训练好的模型一次性生成 2:4 掩码（`m4n2_1d`，可选通道置换恢复精度），再用原超参微调即可；它是 Ampere 时代的训练工具，维护基本冻结，需从源码安装 apex。当前主推的是 **NVIDIA Model Optimizer（简称 ModelOpt，2025 年更名，原 TensorRT Model Optimizer；GitHub 规范仓为 NVIDIA/Model-Optimizer，旧仓名 301 重定向到此，pip 包仍为 nvidia-modelopt）**，一条 `sparsify` 就能产出 2:4 权重，LLM 的 SparseGPT/Wanda 式配方在 examples/llm_sparsity。
2. **调**。ASP 路线按原超参短微调；one-shot 路线多数情况直接可用，必要时 LoRA 恢复。
3. **导**。TensorRT 从 8.0 起支持结构化稀疏（`BuilderFlag.kSPARSE_WEIGHTS` / trtexec 的 sparsity 开关）；ModelOpt 的稀疏 checkpoint 可导出 TensorRT、TensorRT-LLM、vLLM（Sparse-Marlin 内核）、SGLang。
4. **验（最容易被跳过、也最致命）**。稀疏 GEMM 对矩阵的 K/N 对齐倍数有要求（随 TensorRT 版本与数据类型变化，查官方 Structured Sparsity Support Matrix）；**不满足对齐的层会静默回退 dense——不报错、不加速**。必须用 `trtexec --profilingVerbosity=detailed` 或 Nsight 逐层查看 tactic 名，最可靠的办法是同一个引擎分别开启/关闭稀疏构建两次，对比每层耗时。

精度支持方面：Ampere 的 2:4 只覆盖 FP16/BF16/TF32/INT8（FP32 没有结构化稀疏）；Ada/Hopper 在库层加入 FP8；Blackwell 补齐 FP4（4:8）。库分工上，**cuSPARSELt 专做 2:4 稀疏 GEMM，cuSPARSE 是通用 CSR/COO 稀疏线性代数**，两者不要混用。生态现状也要诚实：Neural Magic 2025 年 1 月被 Red Hat 收购，SparseML/DeepSparse/SparseZoo 于 2025 年 6 月 2 日全线 EOL——x86 上非结构化稀疏的商业栈实际断档；继任项目是 llmcompressor（可产出 SparseGPTModifier + 2:4 的 compressed-tensors 检查点给 vLLM），但公开稀疏模型只有个位数，纯稀疏收益约 1.1–1.2 倍，通常要叠加 4bit 量化。NVIDIA 自己的 LLM 优化重心也已转向 FP8/NVFP4 与 Minitron 式结构化剪层。

**演示 4：生产链路导览代码（需 NVIDIA GPU）**

- 环境：CUDA + Ampere 及以上 GPU，Linux；ASP 需源码安装 apex，ModelOpt 为 `pip install nvidia-modelopt`
- 用途：看链路 API 形态；具体键名随版本调整，以官方文档为准
- 预期输出：带 2:4 掩码的 checkpoint；真正是否加速以 TensorRT 逐层 profile 为准

```python
# 路线 A：ASP（Ampere 时代，冻结维护）
from apex.contrib.sparsity import ASP
ASP.prune_trained_model(model, optimizer)   # 生成 2:4 掩码，之后正常微调、保存

# 路线 B：ModelOpt（当前主推）
import modelopt.torch.sparsity as mts
mts.sparsify(model, mode="full_eager",
            config={"default": {"format": "sparse24"}})
# LLM 的 one-shot 配方见 examples/llm_sparsity；导出 TRT/TRT-LLM/vLLM 按官方示例
```

## 8. 收束：什么时候还该剪枝

<PrDecisionFigure />

*图 6：选型先问目标货币，再选路线。*

决策清单：

1. **CNN / 检测 / 分割 / 端侧视觉**：结构化通道剪枝 + 微调/蒸馏仍是常规武器，dense 后端直接受益。
2. **LLM 在线推理提速**：先上量化（W8A8/W4A16）；2:4+量化只在小 batch decode 等带宽受限场景叠加，且必须端到端 profiling。
3. **想要一个任意后端、端侧都能跑的小 dense 模型**：结构化层/维度剪枝 + 蒸馏——这是 Llama-3.2、Minitron 验证过的主路线。
4. **研究与遗留 CPU 栈**：非结构化 one-shot + 专用 kernel；注意 DeepSparse 商业栈已 EOL，多为实验性质。

听到「剪枝 70%、推理提速 2 倍」这类宣传，先问四句：**什么粒度？文件真的变小了吗（稀疏格式还是 dense-with-zeros）？数字是 kernel 时间还是端到端延迟（什么硬件、什么 batch）？精度是谁、用什么数据、在哪个基准上恢复的（免重训 one-shot 与剪后蒸馏的数字不能混着宣传）？**

三句话收尾：**稀疏率是算法指标，加速是系统属性；整齐的零才值钱；剪枝在当代的主场是造小模型，而不是给大模型打零补丁。**

## 9. 自测（答案点击展开）

<Expand title="Q1：prune.l1_unstructured(amount=0.5) 之后，模型为什么没有变快？">

三个必要条件一个都没满足：只挂了 mask，权重仍是 dense 存储（文件不小）、仍走 dense GEMM（没有跳零 kernel）、零的位置随机（即便上通用稀疏 kernel 也摊不平开销）。加速要等压缩表示+专用 kernel，或改走结构化物理缩形。

</Expand>

<Expand title="Q2：同样是 50% 稀疏，2:4 为什么标称 2 倍，随机 50% 不行？">

2:4 的零按固定模式排列，硬件可以靠 2 个索引从每 4 个输入里固定取 2 个，Sparse Tensor Core 一拍做两拍的乘法；随机稀疏的取数位置不规律，索引与访存开销吃掉收益，dense GEMM 又太强。

</Expand>

<Expand title="Q3：SparseGPT 输出的 checkpoint，为什么文件没有变小、默认推理也不加速？">

它保存的是 HuggingFace 标准的 dense 张量，里面含大量零（dense-with-zeros）：零照占字节、dense kernel 照算。要变小需转稀疏/压缩格式（或叠加量化），要加速需 Sparse-Marlin/cuSPARSELt 等专用后端或 2:4 硬件路径。

</Expand>

<Expand title="Q4：工程师在 Llama-3-8B 上 mask 掉 30% 注意力头，困惑度几乎不变，就宣布加速成功——他漏了什么？">

漏了两件事：mask 头不改变任何矩阵形状，延迟不会下降，必须物理缩形；而且现代 LLM 里头的失活是上下文相关的（平均超过 12%，只在特定输入上可消融），GQA 下 K/V 头本就只剩个位数，「困惑度不变」不代表这些头可以静态删除。

</Expand>

<Expand title="Q5：SliceGPT 和 ShortGPT 各自移除的是什么？为什么都不需要稀疏后端？">

SliceGPT 削的是隐藏维——正交旋转对齐后把所有层同一段输入/输出通道物理切窄，权重变成更小的稠密矩阵；ShortGPT 删的是整个 Transformer 层。两者都让 dense 权重矩阵物理缩小，普通 GEMM 直接少算，因此不需要任何稀疏 kernel。

</Expand>

<Expand title="Q6：厂商宣传「剪枝 70%、推理提速 2 倍」，出手前要哪四个证据？">

粒度（非结构化/N:M/结构化？）；存储（文件是否真的变小，还是 dense-with-zeros）；测量层级（kernel 微基准还是端到端延迟，什么硬件、什么 batch）；精度恢复方式与基准（免重训、LoRA 还是全量蒸馏，和谁比）。

</Expand>

<Expand title="Q7（加分）：2:4 kernel 有 1.54–1.63 倍，端到端为什么只有 1.24 倍？这两个数字能直接相减吗？">

不能直接相减——它们不是同一个模型剖面：1.54–1.63 倍是 LLaMA-65B、batch=1 的线性层 CUTLASS kernel 微基准，312→251ms（1.24 倍）是 LLaMA-7B 的端到端生成延迟。共同结论是 softmax/归一化/采样等非 GEMM 段不被稀疏加速，decode 又受权重带宽限制，Amdahl 折扣把线性层收益稀释了。

</Expand>

<Expand title="Q8（加分）：H100 datasheet 的 FP8 稀疏 2 倍与论文实测 1.42 倍矛盾吗？">

不矛盾，要分指令、库、引擎三层：指令层 Hopper 的 wgmma.sp 已支持 FP8 2:4，但实测跨精度跨 shape 平均只有 1.42 倍（arXiv:2402.13499）；cuSPARSELt 库层已含 FP8；Transformer Engine/TensorRT-LLM 等生产引擎没有把 FP8×稀疏接线。datasheet 是理想峰值，生产可用要等栈打通（Blackwell 补 FP4 的 4:8）。

</Expand>
