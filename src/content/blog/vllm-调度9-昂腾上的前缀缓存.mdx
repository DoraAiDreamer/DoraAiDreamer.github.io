block_size 128、MLA 头数硬约束、additional-config 与 AscendStore

软件版本：**vLLM 0.21.0 + vLLM-Ascend**；本文依据 vllm-project/vllm-ascend 官方文档 2026-09 快照，硬件口径以官方最新文档为准。

前八篇都以 NVIDIA GPU 为背景。这一篇讲同一套前缀缓存搬到华为昇腾 NPU 后哪里变了——它也是未来「国产硬件适配」内容的入口，只聚焦与前缀缓存、块大小相关的差异。

## 1. 块大小：GPU 16，昇腾常用 128

最直观的差异是物理块粒度。GPU 上 vLLM 的 `block_size` 默认 16；vLLM-Ascend 的文档与默认配置以 **block_size=128** 为口径（NPU 侧在 `check_and_update_config` 阶段设定块大小，platform 插件注释明确写着 “NPU still sets block_size in check_and_update_config”）。官方调度文档里负载均衡阈值 `long_req_block_threshold=700` 也按 128 解释为”约 89,600 token”（700×128）。

这带来的直接后果（串起[篇 8](/blog/vllm-调度8-前缀缓存从单机到集群)的命中粒度）：

- **最小命中粒度更粗**：一个块要凑满 128 token 才缓存，短共享前缀更容易整块不命中；
- **尾块浪费更大**：未写满的部分不缓存，平均浪费上限从约 15 token 升到约 127 token；
- 好处是单块元数据少、块表和 kernel 调度开销低，契合 NPU 注意力 tiling 的硬件习惯。

## 2. MLA 的头数硬约束

昇腾对 MLA（DeepSeek 类）模型的注意力形状有严格的 tiling 要求。官方 FAQ 原文：启用图模式时，张量并行切分后的 **`num_heads / num_kv_heads` 必须是 128 之一**；DeepSeek-V2-Lite 只有 16 个注意力头，切分后落在集合外，会直接报 `incre_flash_attention_tiling_check` 错误，图模式暂不支持。

这不是前缀缓存本身的限制，但它决定了一个 MLA 模型**能不能在昇腾上按预期跑起来、进而产生可缓存的 KV**。部署 R1/V3 时要先按 TP 度核算切分后的头数（官方还给出 R1 切分后头数须为 128 的约束）。

## 3. 配置入口：additional-config

vLLM-Ascend 的调度相关参数走 `--additional-config`（JSON）传入，而不是 GPU 侧常见的命令行参数；历史环境变量正在迁移淘汰中（官方 Migration Guide 标注 env “will be removed in a future release”）。例如调度器扩展（balance scheduling、short request first 等）都放在 `scheduler_config` 键下。新部署应使用 additional-config，老脚本的 env 写法只在过渡期兼容。

## 4. 跨节点复用：AscendStore 生态

GPU 侧跨实例 KV 复用靠 Mooncake/LMCache/NIXL 等连接器；昇腾有对应的 **AscendStoreConnector**（vLLM-Ascend v0.23.0 起，要求 CANN ≥ 9.1），后端可选：

- **Mooncake**（默认，NPU 协议，支持 SSD offload 与多租户）；
- **Memcache / MemFabric**（A3 上可用 HCCS 高速互联、支持逐层 KV 传输）；
- **云辇（Yuanrong）**。

PD 场景下 P 节点算完写入共享池、D 节点读取，跨请求的公共前缀由此复用。两个边界要注意：`kv_load_failure_policy=recompute` **暂不支持混合注意力模型**（如 DeepSeek 新架构）；这套 Store 本身是独立于 vLLM 主线的昇腾生态组件。

## 5. GPU 与昇腾对照

| 维度 | NVIDIA GPU（0.21 主线） | 昇腾 NPU（vLLM-Ascend） |
| --- | --- | --- |
| 常用 block_size | 16 | 128（NPU 侧设定） |
| 最小缓存/命中粒度 | 细（16 token，尾浪费小） | 粗（128 token，尾浪费大） |
| MLA 形状约束 | 由后端 kernel 决定 | TP 后头数须 ∈ 128，否则图模式报错 |
| 配置方式 | CLI 参数为主 | `--additional-config`（env 迁移中） |
| 跨节点 KV | Mooncake/LMCache/NIXL | AscendStoreConnector + Mooncake/Memcache/云辇 |
| 软件栈 | vLLM 主线 | 需 CANN ≥ 9.1、vllm-ascend 插件 |

核心机制（块哈希、满块才缓存、末块重算、LRU 驱逐）两边相同——变的是块粒度、形状约束、配置入口与网络生态。

## 自测（答案点击展开）

**1.** 同样 200 token 的共享前缀，在 GPU（block 16）和昇腾（block 128）上分别能缓存几个满块？这对短前缀命中意味着什么？

**2.** DeepSeek-V2-Lite 在昇腾图模式下为什么可能起不来？和前缀缓存是什么关系？

**3.** 昇腾上新部署为什么推荐 `--additional-config` 而不是旧的环境变量？

<Expand title="▸参考答案">

1. GPU：200÷16=12 个满块（192 token 可命中）；昇腾：200÷128=1 个满块（128 token 可命中）。块越大最小命中粒度越粗，短共享前缀在昇腾上更容易整块不命中、尾浪费也更大。
2. 它只有 16 个注意力头，TP 切分后头数不在昇腾 tiling 要求的 128 集合内，图模式直接报错。它是”模型能否在 NPU 上跑出 KV”的前置约束，不是缓存逻辑问题；官方称后续版本支持。
3. vLLM-Ascend 正把环境变量迁到 additional-config，并声明 env 将在未来版本移除；新部署用 JSON 配置可避免后续失效，调度器扩展也统一在 scheduler_config 键下。
